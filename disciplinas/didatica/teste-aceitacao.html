Testes de Aceitação em uma Perspectiva de Testes Holísticos

Material de estudo para revisão, compensação de ausências e apoio à aula.

Como usar esta página

  1. Ler as seções na ordem apresentada (tempo estimado de leitura: 20 minutos).
  2. Executar a atividade guiada da seção Atividade guiada.
  3. Registrar suas respostas em uma folha.

Este material está de acordo com a aula presencial sobre testes de aceitação de software. O conteúdo pode ser estudado de forma independente por interessados não presentes na aula.

1. Motivação: entrega rápida e satisfação do cliente

Na literatura de Engenharia de Software, Roger Pressman destaca a ênfase na entrega rápida do software para satisfazer o cliente. Essa frase sintetiza um desafio clássico: entregar com velocidade sem comprometer a qualidade.

Em termos práticos, a satisfação do cliente não depende apenas de cumprir prazos, mas de validar se o produto realmente atende às necessidades do usuário, às regras de negócio e ao contexto de uso para o qual foi criado.

Por que precisamos de testes de aceitação?

Se queremos entrega rápida e satisfação do cliente, precisamos de mecanismos claros para decidir se o que foi construído realmente é aceito como solução do problema. Os testes de aceitação são justamente o conjunto de testes que respondem à pergunta: “Este software está em condição de ser aceito para uso pelo cliente?”.

2. Testes de aceitação: conceitos fundamentais

Testes de aceitação (ou Acceptance Testing, frequentemente associados a User Acceptance Testing – UAT) são testes formais conduzidos para verificar se o sistema atende aos requisitos e expectativas acordadas com o cliente.

Enquanto testes de sistema verificam se o software cumpre sua especificação técnica, os testes de aceitação verificam se o software atende às necessidades de negócio, fluxos reais de uso e critérios de sucesso percebidos pelo cliente.

Posição no ciclo de testes

Em muitas abordagens, os testes de aceitação ocorrem após os testes unitários, os de integração e os de sistema. Eles formam uma “última barreira” antes da liberação em produção para uso oficial.

Quem participa

Dependendo do contexto, os testes de aceitação podem ser conduzidos por usuários finais, representantes do cliente, analistas de negócio, testadores, ou pelo próprio time de desenvolvimento em nome do cliente.

Testes de aceitação e contrato

Em muitos projetos, os testes de aceitação estão vinculados a contratos, SLAs e critérios de aceite formal. Somente após a aprovação nesses testes o fornecedor pode considerar o sistema entregue.

3. Testes holísticos (Holistic Testing)

Lisa Crispin e Janet Gregory propõem o termo holistic testing para descrever uma abordagem em que a qualidade é responsabilidade de toda a equipe, e em que as atividades de teste são planejadas ao longo de todo o ciclo de desenvolvimento.

Em vez de tratar testes como uma fase isolada ao final do projeto, o modelo de testes holísticos mapeia diferentes tipos de teste – técnicos e voltados ao negócio – distribuídos desde a concepção até o uso em produção, com ciclos de feedback contínuos.

Onde entram os testes de aceitação?

No modelo de testes holísticos, os testes de aceitação fazem parte dos testes voltados ao negócio (business-facing tests), geralmente focados em validar se o produto entrega o valor esperado pelo cliente e pelas partes interessadas.

4. Exemplo: Nave Explorer

Para tornar os conceitos mais concretos, vamos usar um exemplo fictício: o sistema de controle da nave espacial Explorer, utilizada em missões de exploração planetária.

Uma das funcionalidades críticas desse sistema é o modo de pouso automático em planetas autorizados. Do ponto de vista da agência responsável pela missão e da tripulação, aceitar o software significa confiar que esse modo de pouso funciona de forma segura e consistente.

História de usuário: Pouso automático

Como piloto da nave Explorer, quero ativar o modo de pouso automático em um planeta autorizado, para que a nave execute o pouso com segurança sem que eu precise controlar manualmente todos os detalhes.

Critério de aceitação (Given–When–Then)

Um critério de aceitação para essa história pode ser descrito no formato Given–When–Then (Dado–Quando–Então):

  • Dado que a nave Explorer está em órbita estável em torno de um planeta autorizado, com combustível acima de 30% e todos os sistemas críticos operacionais;
  • Quando o piloto selecionar esse planeta e acionar o botão “Pouso Automático” no painel de controle;
  • Então o sistema deve calcular a trajetória de descida, iniciar a sequência de pouso e exibir, ao final, a mensagem “Pouso concluído com sucesso” para a tripulação.

Este critério pode ser transformado em um caso de teste de aceitação, detalhando estado inicial, dados de entrada, passos de execução e resultado esperado.

Conexão com satisfação do cliente

Se esse critério de aceitação não for atendido, o cliente (a agência responsável pela missão) não pode aceitar o software para uso em missões reais, mesmo que vários testes unitários e de integração tenham sido bem-sucedidos.

5. Atividade guiada

Esta atividade tem como objetivo consolidar o entendimento de testes de aceitação e de critérios de aceitação em formato Given–When–Then, dentro da perspectiva de testes holísticos.

  1. Escolha de funcionalidade
    Escolha outra funcionalidade da nave Explorer, por exemplo:
    • Ativar modo de emergência.
    • Configurar uma nova rota de viagem.
    • Gerar um relatório de status da missão.
    • Seja criativo...
  2. Escreva a história de usuário
    Use o formato: “Como [tipo de usuário], quero [ação] para [benefício/resultado esperado]”.
  3. Defina pelo menos dois critérios de aceitação
    Para cada critério, use o formato Given–When–Then, garantindo que as condições sejam claras e verificáveis.
  4. Transforme um critério em caso de teste
    Complete o modelo abaixo em uma folha: 
    Nome do caso de teste: _________________________
Estado inicial / pré-condições:
- _____________________________________________
- _____________________________________________

Entradas / dados de teste:
- _____________________________________________
- _____________________________________________

Passos para execução:
1) ____________________________________________
2) ____________________________________________
3) ____________________________________________

Resultado esperado:
- _____________________________________________
  5. Reflexão
    Relacione seu critério de aceitação com o modelo de testes holísticos: em que momento do ciclo ele seria planejado e executado? Quem participaria?
