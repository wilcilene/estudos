1. Visão geral

Quando um usuário faz login, a aplicação precisa responder a duas perguntas: quem é essa pessoa? e o que ela pode acessar?

A primeira pergunta está relacionada à autenticação. A segunda à autorização ou controle de acesso.

Palavras-chave desta aula:

  • Autenticação: verificar identidade.
  • Autorização: verificar permissões.
  • Sessão: estado mantido no servidor.
  • JWT: token assinado enviado pelo cliente.
  • Middleware: função intermediária entre requisição e resposta.
  • Rota protegida: exige login para acesso.
Ideia central: autenticar é provar quem o usuário é; autorizar é decidir o que ele pode fazer dentro da API.

2. Autenticação com sessões

Na autenticação por sessão, o servidor guarda o estado do login. O navegador recebe um identificador de sessão, normalmente em cookie, e o envia automaticamente nas próximas requisições.

2.1 Fluxo básico

  1. Usuário envia login e senha.
  2. Servidor valida as credenciais.
  3. Servidor cria uma sessão.
  4. Servidor envia um cookie com o identificador da sessão.
  5. Nas próximas requisições, o navegador envia esse cookie.
  6. O servidor consulta a sessão e reconhece o usuário.

2.2 Exemplo simples com Express

const express = require('express');
const session = require('express-session');

const app = express();
app.use(express.json());

app.use(session({
  secret: 'segredo-super-seguro',
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true
  }
}));

app.post('/login', (req, res) => {
  const { email, senha } = req.body;

  if (email === 'admin@email.com' && senha === '123456') {
    req.session.usuario = {
      id: 1,
      nome: 'Administrador',
      perfil: 'admin'
    };

    return res.json({ mensagem: 'Login realizado com sucesso' });
  }

  res.status(401).json({ erro: 'Credenciais inválidas' });
});

app.get('/perfil', (req, res) => {
  if (!req.session.usuario) {
    return res.status(401).json({ erro: 'Não autenticado' });
  }

  res.json(req.session.usuario);
});

app.post('/logout', (req, res) => {
  req.session.destroy(() => {
    res.json({ mensagem: 'Logout realizado' });
  });
});

app.listen(3000, () => {
  console.log('Servidor rodando na porta 3000');
});
express-session
Middleware que permite criar e gerenciar sessões no Express.
req.session.usuario
Armazena os dados do usuário autenticado na sessão.
httpOnly
Impede acesso ao cookie por JavaScript no navegador, aumentando a segurança.

Em sessão, o servidor “lembra” do usuário. O cliente carrega apenas o identificador da sessão, não os dados completos do login.

3. Autenticação com JWT

JWT significa JSON Web Token. Nesse modelo, o servidor gera um token assinado após o login, e o cliente envia esse token nas próximas requisições, geralmente no cabeçalho Authorization.

3.1 Fluxo básico com JWT

  1. Usuário envia login e senha.
  2. Servidor valida as credenciais.
  3. Servidor gera um token JWT assinado.
  4. Cliente armazena o token.
  5. Cliente envia o token nas próximas requisições.
  6. Servidor valida o token antes de liberar o acesso.

3.2 Instalando a biblioteca

npm install jsonwebtoken

3.3 Exemplo de login com JWT

const express = require('express');
const jwt = require('jsonwebtoken');

const app = express();
app.use(express.json());

const SEGREDO_JWT = 'chave-super-secreta';

app.post('/login', (req, res) => {
  const { email, senha } = req.body;

  if (email === 'admin@email.com' && senha === '123456') {
    const usuario = {
      id: 1,
      nome: 'Administrador',
      perfil: 'admin'
    };

    const token = jwt.sign(usuario, SEGREDO_JWT, {
      expiresIn: '1h'
    });

    return res.json({
      mensagem: 'Login realizado com sucesso',
      token
    });
  }

  res.status(401).json({ erro: 'Credenciais inválidas' });
});

app.listen(3000, () => {
  console.log('Servidor rodando na porta 3000');
});

3.4 Middleware para proteger rotas com JWT

function verificarToken(req, res, next) {
  const authHeader = req.headers.authorization;

  if (!authHeader) {
    return res.status(401).json({ erro: 'Token não enviado' });
  }

  const partes = authHeader.split(' ');

  if (partes.length !== 2 || partes[0] !== 'Bearer') {
    return res.status(401).json({ erro: 'Formato do token inválido' });
  }

  const token = partes[1];

  try {
    const usuarioDecodificado = jwt.verify(token, SEGREDO_JWT);
    req.usuario = usuarioDecodificado;
    next();
  } catch (erro) {
    return res.status(401).json({ erro: 'Token inválido ou expirado' });
  }
}

app.get('/perfil', verificarToken, (req, res) => {
  res.json({
    mensagem: 'Rota protegida acessada com sucesso',
    usuario: req.usuario
  });
});

Exemplo de cabeçalho enviado pelo cliente:

Authorization: Bearer SEU_TOKEN_AQUI

No JWT, o servidor não precisa guardar a sessão do usuário da mesma forma que no modelo tradicional. O cliente carrega o token e o servidor apenas verifica sua assinatura e validade.

3.5 Outros tipos de autenticação e por que o JWT é tão usado

JWT não é a única forma de autenticação. Na prática, existem vários modelos, e cada um faz mais sentido em determinados contextos.

Outros tipos comuns

  • Sessão com cookie: o servidor guarda o estado do login e o navegador envia automaticamente um cookie com o identificador da sessão.
  • HTTP Basic Auth: usuário e senha são enviados no cabeçalho da requisição. É simples, mas não é a melhor escolha para aplicações modernas com login persistente.
  • Token opaco: o cliente envia um token que não carrega dados legíveis; o servidor consulta esse token para descobrir quem é o usuário.
  • OAuth 2.0 / OpenID Connect: usados quando a autenticação envolve provedores externos, como login com Google ou GitHub.
  • API Key: comum na autenticação entre sistemas e serviços, mas não é a abordagem mais indicada para login de usuário final.

Por que o JWT é recomendado?

  • É stateless: o servidor não precisa manter uma sessão tradicional para cada usuário autenticado.
  • Funciona muito bem em APIs: especialmente quando o front-end está separado do back-end e faz requisições com fetch ou axios.
  • É portátil: pode ser validado em diferentes serviços da aplicação.
  • Carrega informações úteis: como id do usuário, perfil, permissões e expiração.
  • É padronizado: bibliotecas e frameworks já oferecem suporte pronto para geração e validação.

Mas...

JWT nem sempre é a melhor escolha. Em aplicações menores e mais simples, por exemplo, autenticação por sessão pode ser mais simples de implementar e manter. O importante é entender o contexto do projeto e escolher a estratégia adequada.

4. Controle de acesso em APIs

Autenticar não basta. Muitas vezes precisamos verificar se o usuário pode acessar uma determinada ação, como excluir registros, acessar relatórios ou administrar outros usuários.

4.1 Exemplo com perfil de usuário

function verificarAdmin(req, res, next) {
  if (!req.usuario) {
    return res.status(401).json({ erro: 'Não autenticado' });
  }

  if (req.usuario.perfil !== 'admin') {
    return res.status(403).json({ erro: 'Acesso negado' });
  }

  next();
}

app.delete('/usuarios/:id', verificarToken, verificarAdmin, (req, res) => {
  res.json({ mensagem: 'Usuário removido com sucesso' });
});
401 Unauthorized
Usuário não está autenticado ou token está ausente/inválido.
403 Forbidden
Usuário está autenticado, mas não tem permissão para aquela ação.

4.2 Lógica importante

  • Primeiro verificamos se o usuário está autenticado.
  • Depois verificamos se ele tem o perfil ou permissão necessária.
  • Esse controle normalmente é implementado com middlewares reutilizáveis.

5. Sessões x JWT

Sessões e JWT resolvem o problema do login, mas funcionam de maneiras diferentes. O importante é entender a lógica de cada modelo antes de decidir qual usar.

Critério Sessões JWT
Estado do login Guardado no servidor Representado no token enviado pelo cliente
Transporte Normalmente via cookie Normalmente via header Authorization
Logout Destrói a sessão no servidor Exige estratégia de expiração, remoção no cliente ou revogação
Uso comum Apps tradicionais com sessão APIs, SPAs e integrações entre serviços

6. Exemplo de consumo no front-end com JavaScript

Como já estudamos fetch e consumo de APIs, vamos trabalhar com login.

6.1 Enviando login com fetch

async function fazerLogin() {
  const email = 'admin@email.com';
  const senha = '123456';

  const resposta = await fetch('http://localhost:3000/login', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({ email, senha })
  });

  const dados = await resposta.json();

  if (!resposta.ok) {
    alert(dados.erro);
    return;
  }

  localStorage.setItem('token', dados.token);
  alert('Login realizado com sucesso!');
}

6.2 Acessando rota protegida com JWT

async function carregarPerfil() {
  const token = localStorage.getItem('token');

  const resposta = await fetch('http://localhost:3000/perfil', {
    headers: {
      'Authorization': `Bearer ${token}`
    }
  });

  const dados = await resposta.json();

  if (!resposta.ok) {
    console.log('Erro:', dados.erro);
    return;
  }

  console.log('Usuário autenticado:', dados.usuario);
}

Esse exemplo ajuda a conectar os conteúdos já estudados: rota REST, middleware, status code, JSON, fetch e agora autenticação.

7. Exercícios

Importante: grupos que já implementaram autenticação e autorização no projeto não precisam fazer o exercício desta página. Grupos que ainda não implementaram devem entregar o exercício.

Para ser considerado “já implementado”, o projeto deve ter pelo menos:

  • Uma rota de login funcionando.
  • Uma forma de manter o usuário autenticado (sessão ou JWT).
  • Pelo menos uma rota protegida.
  • Pelo menos uma verificação de permissão ou perfil de acesso.

7.1 Exercício básico obrigatório para quem ainda não implementou

Se o projeto do grupo ainda não possui autenticação e autorização, implemente uma versão mínima com JavaScript no back-end usando Express.

Exercício básico

  • Crie uma rota POST /login com usuário fixo para teste.
  • Após login válido, gere uma autenticação simples usando sessão ou JWT.
  • Crie uma rota protegida GET /perfil que só pode ser acessada por usuário autenticado.
  • Crie uma rota DELETE /admin/exemplo acessível apenas por usuário com perfil admin.
  • Retorne 401 quando o usuário não estiver autenticado.
  • Retorne 403 quando estiver autenticado, mas sem permissão.

7.2 Estrutura mínima esperada

POST   /login
GET    /perfil
DELETE /admin/exemplo

7.3 Exemplo de usuário fixo para teste

{
  "email": "admin@email.com",
  "senha": "123456",
  "perfil": "admin"
}

7.4 O que deve ser observado

  • O login funciona corretamente?
  • A rota protegida exige autenticação?
  • A rota administrativa exige permissão adequada?
  • Os status 401 e 403 foram usados corretamente?
  • A implementação está organizada e compreensível?

O objetivo deste exercício não é criar um sistema completo de autenticação, mas implementar o fluxo básico para entender como proteger rotas e controlar acesso na API.
