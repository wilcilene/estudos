Conceitos Básicos de Sistemas de Banco de Dados

Antes de projetar tabelas ou escrever SQL, é preciso entender por que sistemas de banco de dados existem: quais problemas de sistemas de arquivos eles resolvem e como um SGBD organiza a fronteira entre dado, esquema e aplicação.

Objetivos de aprendizagem

  • Diferenciar dado, informação e conhecimento em um contexto de engenharia.
  • Explicar as limitações de manter dados em sistemas de arquivos comuns.
  • Definir o que é um SGBD e listar suas principais funções.
  • Diferenciar esquema (schema) de instância (instance) de um banco de dados.
  • Explicar independência de dados lógica e física.
  • Descrever a arquitetura ANSI/SPARC de três esquemas.

1. Dado, informação e conhecimento

Em engenharia de computação é comum tratar esses três termos como sinônimos, mas eles representam níveis diferentes de processamento:

  • Dado — um valor bruto, sem contexto: 23.4, "2026-08-05", 0x1F.
  • Informação — o dado interpretado dentro de um contexto: "a temperatura do sensor 3 às 14h foi 23,4 °C".
  • Conhecimento — o padrão extraído de várias informações, usado para decidir: "a temperatura média da sala sobe 2 °C por hora durante a tarde; acionar o ar-condicionado às 13h".

Um banco de dados armazena e organiza dados; é o esquema, as consultas e a aplicação que os transformam em informação — e, eventualmente, em conhecimento.

2. Por que não usar apenas arquivos?

Antes dos SGBDs, sistemas guardavam dados em arquivos próprios de cada aplicação (texto, CSV, binários proprietários). Isso funciona para escala pequena, mas cria problemas conhecidos à medida que o sistema cresce:

Sistemas de arquivos × SGBD
Problema em sistemas de arquivos Como um SGBD ataca isso
Redundância e inconsistência — o mesmo dado duplicado em vários arquivos, podendo ficar desatualizado em um deles. Um único repositório lógico compartilhado por todas as aplicações.
Dificuldade de acesso — cada nova consulta exige escrever um programa novo para ler o arquivo. Linguagem declarativa (SQL) para consultar dados sem programar o acesso físico.
Isolamento de dados — formatos diferentes por aplicação dificultam integração. Esquema único, com tipos e relacionamentos definidos centralmente.
Anomalias de concorrência — dois processos escrevendo ao mesmo tempo corrompem o arquivo. Controle de concorrência (locks, MVCC) e transações.
Falta de atomicidade — uma queda de energia no meio de uma operação deixa dados parcialmente gravados. Transações com propriedades ACID e recuperação após falhas.
Segurança fraca — controle de acesso limitado ao sistema operacional de arquivos. Permissões por usuário, papel (role) e nível de dado (linha/coluna).

3. O que é um SGBD

Um Sistema Gerenciador de Banco de Dados (SGBD) é o software que fica entre a aplicação e os dados armazenados, oferecendo uma camada de abstração e controle. Suas funções principais:

  • Definição de dados — linguagem para descrever estruturas (DDL).
  • Manipulação de dados — linguagem para inserir, alterar, remover e consultar (DML).
  • Controle de concorrência — permitir múltiplos usuários/processos acessando os dados ao mesmo tempo sem corrupção.
  • Recuperação de falhas — voltar a um estado consistente após uma queda do sistema.
  • Segurança e controle de acesso — autenticação, autorização e auditoria.

Exemplos que podem ser usados nas práticas de laboratório: PostgreSQL e MySQL (SGBDs cliente-servidor) e SQLite (SGBD embarcado, comum em aplicações mobile e sistemas embarcados).

4. Esquema × instância

Dois termos que serão usados o semestre todo:

  • Esquema (schema) — a estrutura definida em tempo de projeto: quais tabelas existem, quais colunas, tipos e relacionamentos. Muda raramente.
  • Instância (instance) — os dados armazenados em um momento específico. Muda a cada operação de escrita.

Analogia com programação orientada a objetos: esquema está para instância assim como classe está para objeto. A classe define a forma; o objeto é uma ocorrência concreta dela em memória.

5. Independência de dados

Um dos principais objetivos de um SGBD é permitir que o esquema evolua sem quebrar as aplicações que o usam — o mesmo princípio de estabilidade de interface que se busca em APIs de software:

  • Independência lógica — é possível alterar o esquema conceitual (ex.: adicionar uma tabela ou coluna) sem reescrever as aplicações existentes.
  • Independência física — é possível mudar a forma de armazenamento físico (ex.: trocar o tipo de índice, particionar uma tabela) sem alterar o esquema conceitual nem as aplicações.
