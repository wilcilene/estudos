Integração

Desenvolvimento de aplicações com banco de dados

Em todos os tópicos anteriores, rodamos SQL diretamente em um cliente de banco. Mas, na prática, é uma aplicação — escrita em Java, Python, JavaScript, etc. — quem precisa falar com o banco. Hoje vamos fechar o ciclo: como uma aplicação real se conecta, envia comandos e se protege de erros e ataques. Vamos acompanhar a equipe que desenvolve o sistema da Central de Resgate Estelar.

O que vocês vão aprender aqui

  • Entender o papel dos drivers ODBC/JDBC na comunicação aplicação ↔ banco.
  • Entender o que um ORM resolve e o que ele esconde.
  • Entender por que uma aplicação usa um pool de conexões, em vez de abrir uma conexão nova a cada operação.
  • Reconhecer e prevenir SQL injection com prepared statements.

1. A Central de Resgate Estelar

🚀 Central de Resgate Estelar

A equipe está construindo o sistema que recebe pedidos de socorro de naves em apuros, registra cada chamado no banco de dados e aciona a nave de resgate mais próxima. O sistema roda em um servidor e precisa conversar com um banco de dados relacional continuamente, atendendo vários operadores ao mesmo tempo.

A primeira pergunta da equipe: como o código da aplicação, escrito em uma linguagem de programação, consegue enviar comandos SQL para o banco e receber os resultados de volta?

2. Drivers ODBC e JDBC: a ponte com o banco

A aplicação não "fala" diretamente o protocolo interno do SGBD. Ela usa um driver — uma biblioteca que traduz comandos da linguagem de programação para o protocolo que o banco entende, e traduz as respostas do banco de volta para estruturas que a aplicação consegue usar.

ODBC e JDBC
DriverContexto de uso
ODBC (Open Database Connectivity) Padrão independente de linguagem, amplamente usado para conectar aplicações a diferentes SGBDs através de uma interface comum em C.
JDBC (Java Database Connectivity) Padrão específico para aplicações Java, com uma API orientada a objetos para abrir conexões, executar comandos e percorrer resultados. 
// Exemplo ilustrativo em Java com JDBC
Connection conexao = DriverManager.getConnection(
    "jdbc:mysql://localhost:3306/resgate_estelar", "usuario", "senha");

Statement comando = conexao.createStatement();
ResultSet resultado = comando.executeQuery(
    "SELECT * FROM chamado_socorro WHERE status = 'pendente'");

Note que, por trás dessas poucas linhas, o driver está abrindo uma conexão de rede com o SGBD, autenticando o usuário, enviando o comando SQL e convertendo as linhas da resposta em objetos que o código Java consegue percorrer.

3. ORMs: mapeando tabelas para objetos

Escrever SQL manualmente para cada operação funciona, mas em um sistema grande isso significa muito código repetitivo. Um ORM (Object-Relational Mapper) mapeia cada tabela para uma classe e cada linha para um objeto, permitindo trabalhar com o banco usando a linguagem de programação em vez de escrever SQL diretamente:

# Exemplo ilustrativo em Python com um ORM
chamados_pendentes = ChamadoSocorro.objects.filter(status='pendente')

for chamado in chamados_pendentes:
    print(chamado.nave_solicitante, chamado.coordenadas)

Por trás dessas duas linhas, o ORM gera e executa algo equivalente a SELECT * FROM chamado_socorro WHERE status = 'pendente', e converte cada linha do resultado em um objeto ChamadoSocorro.

Conceito: o que o ORM ganha e o que ele esconde

Um ORM acelera o desenvolvimento e reduz SQL repetitivo, mas também esconde o comando real que está sendo executado. Em consultas simples isso não é problema; em consultas complexas ou que precisam de alto desempenho, a equipe de desenvolvimento ainda precisa entender o SQL gerado por baixo — tudo o que vocês estudaram até aqui continua relevante mesmo usando um ORM.

4. Pool de conexões

Abrir uma conexão com o banco não é instantâneo: envolve autenticação, estabelecimento de rede e alocação de recursos no SGBD. Se a Central de Resgate abrisse e fechasse uma conexão nova para cada chamado de socorro recebido, o sistema ficaria lento e sobrecarregaria o banco com conexões.

A solução é um pool de conexões: a aplicação abre um conjunto de conexões quando inicia e as mantém abertas, reaproveitando-as entre as operações.

Aplicação inicia — um pool com, por exemplo, 10 conexões já abertas é criado.
Operador registra um chamado — a aplicação pede uma conexão livre do pool, em vez de abrir uma nova.
Comando é executado — o INSERT do novo chamado roda usando essa conexão emprestada.
Conexão é devolvida — em vez de ser fechada, a conexão volta para o pool, pronta para a próxima operação.

💡 Por que isso importa para quem projeta o banco

O tamanho do pool de conexões afeta diretamente quantas operações simultâneas o banco aguenta. Um pool pequeno pode gerar filas de espera; um pool grande demais pode sobrecarregar o SGBD com mais conexões do que ele consegue administrar com eficiência.

5. SQL injection: o ataque que explora SQL montado na mão

Suponha que a equipe monte a consulta de busca de chamados concatenando o texto digitado pelo operador diretamente no SQL:

// NUNCA faça isso
String idDigitado = campoTexto.getText();
String sql = "SELECT * FROM chamado_socorro WHERE id_chamado = " + idDigitado;
comando.executeQuery(sql);

Se um operador mal-intencionado digitar, no lugar de um número, o texto 0 OR 1=1, o comando final se torna:

SELECT * FROM chamado_socorro WHERE id_chamado = 0 OR 1=1

1=1 é sempre verdadeiro, então essa condição retorna todos os chamados da tabela, não apenas um. Com entradas mais elaboradas, esse tipo de ataque pode ler, alterar ou apagar dados que o operador nunca deveria acessar. Isso é SQL injection: o texto digitado pelo usuário é interpretado como parte do comando SQL, em vez de apenas como um valor.

🚨 A causa raiz: misturar dado com comando

O problema não é "o que o operador digitou" — é que o código tratou a entrada do operador como parte do código SQL, em vez de tratá-la como um valor dentro de um comando fixo.

6. Prevenindo com prepared statements

A correção é usar um prepared statement: o comando SQL é enviado ao banco com um espaço reservado (?) no lugar do valor, e o valor digitado é enviado separadamente, nunca como texto a ser interpretado como SQL:

String sql = "SELECT * FROM chamado_socorro WHERE id_chamado = ?";
PreparedStatement comando = conexao.prepareStatement(sql);
comando.setInt(1, Integer.parseInt(idDigitado));
ResultSet resultado = comando.executeQuery();
Linha a linha: a defesa com prepared statement
TrechoO que significa
WHERE id_chamado = ? O ? é um espaço reservado. O driver já sabe, pelo comando, que ali vai existir exatamente um valor — nunca um trecho de SQL.
comando.setInt(1, ...) Define o valor do primeiro espaço reservado como um número inteiro. Se o operador tentasse digitar 0 OR 1=1, essa conversão para inteiro simplesmente falharia — o texto nunca chega a ser interpretado como SQL.
comando.executeQuery(); Executa o comando já com o valor embutido de forma segura pelo próprio driver, não por concatenação de texto.

Com o prepared statement, mesmo que o operador digite algo malicioso, esse texto é tratado estritamente como o valor de um parâmetro — nunca como parte da estrutura do comando SQL. É por isso que prepared statements (ou o equivalente fornecido por um ORM) são a defesa padrão contra SQL injection.

🤔 Confira se entendeu

Por que a Central de Resgate Estelar usa um pool de conexões em vez de abrir uma conexão nova para cada chamado?

Porque abrir uma conexão é custoso (autenticação, rede, alocação de recursos). Reaproveitar conexões já abertas através de um pool evita esse custo repetido e evita sobrecarregar o banco com um número excessivo de conexões simultâneas.

Por que "SELECT * FROM chamado_socorro WHERE id_chamado = " + idDigitado é perigoso, mesmo que pareça funcionar na maioria dos testes?

Porque concatena a entrada do usuário diretamente no comando SQL. Uma entrada como "0 OR 1=1" deixa de ser apenas um valor e passa a alterar a lógica do comando, retornando dados que não deveriam ser acessados — isso é SQL injection.
