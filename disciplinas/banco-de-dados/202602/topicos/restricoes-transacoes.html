Restrições de integridade e transações (ACID)

Vocês já usam CHECK, UNIQUE e NOT NULL desde a DDL — hoje vamos revisá-los rapidamente e depois resolver um problema novo: o que acontece quando uma operação de negócio precisa de mais de um comando SQL para ser concluída? Vamos abrir o cofre central do RoboBank, o banco que atende contas de robôs.

O que vocês vão aprender aqui

  • Revisar CHECK, UNIQUE e NOT NULL como restrições de integridade.
  • Entender por que algumas operações precisam de mais de um comando SQL.
  • Usar START TRANSACTION, COMMIT e ROLLBACK.
  • Explicar cada letra da sigla ACID com um exemplo concreto.

1. O cofre do RoboBank

🏦 RoboBank

Cada robô tem uma conta de créditos. O saldo nunca pode ficar negativo — essa é uma regra inegociável do banco.

CREATE TABLE conta_robo (
  id_conta INT PRIMARY KEY AUTO_INCREMENT,
  titular_robo VARCHAR(60) NOT NULL UNIQUE,
  saldo DECIMAL(12,2) NOT NULL DEFAULT 0,
  CONSTRAINT chk_saldo_positivo CHECK (saldo >= 0)
);

Rapidinho, para quem já viu isso na DDL: NOT NULL torna o titular obrigatório, UNIQUE impede dois robôs com a mesma conta, e CHECK (saldo >= 0) bloqueia qualquer UPDATE que deixaria o saldo negativo — o banco nunca aceita a linha, não importa o que a aplicação tente fazer.

2. O problema: uma transferência não é um comando só

Transferir 100 créditos do robô A para o robô B exige dois comandos:

UPDATE conta_robo SET saldo = saldo - 100 WHERE titular_robo = 'Unidade-A';
UPDATE conta_robo SET saldo = saldo + 100 WHERE titular_robo = 'Unidade-B';

🚨 E se a energia cair entre os dois comandos?

Se o primeiro UPDATE rodar e, antes do segundo, a conexão cair ou o servidor reiniciar, o robô A perde 100 créditos e o robô B nunca recebe nada. Créditos somem do sistema. É exatamente esse risco que uma transação elimina.

3. Agrupando comandos em uma transação

START TRANSACTION;

UPDATE conta_robo SET saldo = saldo - 100 WHERE titular_robo = 'Unidade-A';
UPDATE conta_robo SET saldo = saldo + 100 WHERE titular_robo = 'Unidade-B';

COMMIT;
Linha a linha: uma transferência segura
TrechoO que significa
START TRANSACTION; Abre um bloco: a partir daqui, nenhuma alteração é gravada em definitivo até que a transação seja confirmada.
UPDATE ... SET saldo = saldo - 100 ... Debita o robô A. A mudança já existe dentro da transação, mas ainda não é definitiva nem visível para outras conexões.
UPDATE ... SET saldo = saldo + 100 ... Credita o robô B, ainda dentro do mesmo bloco.
COMMIT; Confirma o bloco inteiro de uma vez: as duas alterações se tornam permanentes juntas, ou nenhuma delas se torna.

Se algo der errado no meio do caminho — por exemplo, o segundo UPDATE violar o CHECK (saldo >= 0) porque o robô B não existe — nós desfazemos tudo com ROLLBACK em vez de COMMIT:

START TRANSACTION;

UPDATE conta_robo SET saldo = saldo - 100 WHERE titular_robo = 'Unidade-A';
-- algo deu errado aqui
ROLLBACK;

ROLLBACK desfaz tudo o que aconteceu desde o START TRANSACTION, como se a transação nunca tivesse existido — o robô A recupera os 100 créditos que havia "perdido" dentro do bloco.

4. ACID: as quatro garantias por trás do COMMIT

ACID na transferência do RoboBank
PropriedadeO que garanteNo nosso exemplo
Atomicidade A transação acontece por inteiro, ou não acontece nada. É impossível o robô A perder créditos sem o robô B recebê-los.
Consistência A transação leva o banco de um estado válido para outro estado válido, respeitando todas as restrições. O CHECK (saldo >= 0) nunca é violado, nem durante, nem depois da transação.
Isolamento Transações acontecendo ao mesmo tempo não enxergam os resultados parciais umas das outras. Se duas transferências envolvendo o robô A acontecerem ao mesmo tempo, uma não vê o saldo "no meio do caminho" da outra.
Durabilidade Depois do COMMIT, o resultado sobrevive mesmo a uma queda de energia imediatamente em seguida. Uma vez confirmada, a transferência não "some" se o servidor reiniciar um segundo depois.

Conceito: isolamento tem níveis

Na prática, "isolamento total" entre transações simultâneas tem um custo de desempenho, então os SGBDs oferecem níveis de isolamento configuráveis, trocando um pouco de rigor por velocidade. Esse ajuste fino é um tópico avançado — por enquanto, o que importa é saber que o problema existe e que o SGBD dá ferramentas para controlá-lo.

🤔 Confira se entendeu

Por que não bastava rodar os dois UPDATEs um atrás do outro, sem START TRANSACTION?

Porque, sem a transação, cada UPDATE é confirmado isoladamente. Se o processo for interrompido entre os dois comandos, o débito do robô A já estaria confirmado e o crédito do robô B, não — os créditos simplesmente desapareceriam.

Qual propriedade do ACID é violada se, depois de um COMMIT confirmado, uma queda de energia faz o banco "esquecer" a transferência?

A durabilidade, que garante que o resultado de uma transação confirmada sobrevive a falhas do sistema.
