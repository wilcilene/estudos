Normalização

Dependências funcionais e as três primeiras formas normais

Até aqui vocês modelaram pensando em entidades e relacionamentos. A normalização é uma segunda lente, mais matemática: ela olha para uma tabela já existente e pergunta "essa estrutura está causando problemas de redundância e inconsistência?". Vamos destrinchar isso com o arquivo bagunçado de uma embaixada intergaláctica.

O que vocês vão aprender aqui

  • Reconhecer anomalias de inserção, atualização e remoção em uma tabela mal estruturada.
  • Definir dependência funcional e usar a notação A → B.
  • Levar uma tabela à 1ª Forma Normal, eliminando grupos repetidos.
  • Levar uma tabela à 2ª Forma Normal, eliminando dependência parcial da chave.
  • Levar uma tabela à 3ª Forma Normal, eliminando dependência transitiva.

1. O arquivo bagunçado da embaixada

🛸 A embaixada intergaláctica

A embaixada registra visitas diplomáticas numa única planilha gigante. Cada linha é uma visita, mas várias informações se repetem de um jeito que vai dar problema.

2. Dependência funcional: a régua que vamos usar

Dizemos que A determina funcionalmente B (escrevemos A → B) quando, para cada valor de A, existe exatamente um valor de B associado. No nosso arquivo:

Dependências funcionais identificadas
DependênciaEm palavras
id_visita → data_visitaCada visita tem uma única data.
id_visita → embaixadorCada visita está associada a um único embaixador.
embaixador → email_embaixadorCada embaixador tem um único e-mail — essa dependência não passa pela visita, ela é direta.
planeta → capital_planetaCada planeta tem uma única capital — de novo, independente da visita.

É exatamente essa última coluna — "não passa pela visita" — que vai nos guiar pelas três formas normais.

3. Primeira Forma Normal (1FN): acabar com grupos repetidos

A coluna idiomas_falados guarda mais de um valor dentro da mesma célula ("Glorbiano, Common") — isso viola a atomicidade exigida pela 1FN: cada célula deve conter um único valor, de um único tipo.

Conceito: o que a 1FN exige

Uma tabela está na 1ª Forma Normal quando todos os seus atributos são atômicos (um valor por célula) e não existem grupos repetidos de colunas (como idioma1, idioma2, idioma3).

Para resolver, tiramos os idiomas para uma tabela própria, onde cada linha é um par visita + idioma:

CREATE TABLE visita_idioma (
  id_visita INT NOT NULL,
  idioma VARCHAR(40) NOT NULL,
  PRIMARY KEY (id_visita, idioma)
);

A tabela principal passa a ter uma linha por visita, sem repetir idiomas na mesma célula — já está na 1FN. Mas ainda tem os outros dois problemas.

4. Segunda Forma Normal (2FN): acabar com dependência parcial

A 2FN só faz sentido discutir quando a chave primária é composta (mais de uma coluna) — é exatamente o caso de visita_idioma, cuja chave é (id_visita, idioma).

Conceito: dependência parcial

Uma dependência é parcial quando um atributo não-chave depende de apenas parte da chave composta, em vez de depender da chave inteira. Se eu tivesse colocado data_visita dentro de visita_idioma, ela dependeria só de id_visita — não precisaria do idioma para ser determinada. Isso seria uma dependência parcial, e violaria a 2FN.

No nosso caso, não cometemos esse erro: visita_idioma não tem nenhum atributo além da própria chave composta, então ela já respeita a 2FN automaticamente. A tabela principal, visita_diplomatica, tem chave simples (id_visita), então a 2FN não se aplica a ela — toda tabela com chave simples já está, por definição, na 2FN.

5. Terceira Forma Normal (3FN): acabar com dependência transitiva

Voltando à tabela principal: embaixador → email_embaixador e planeta → capital_planeta não dependem de id_visita diretamente — dependem de embaixador e planeta, que por sua vez dependem de id_visita. Esse é um caminho indireto, chamado dependência transitiva, e é exatamente o que a 3FN proíbe.

Conceito: dependência transitiva

Existe dependência transitiva quando id_visita → embaixador e embaixador → email_embaixador — ou seja, email_embaixador depende de id_visita só "por tabela", através de embaixador. A 3FN exige que todo atributo não-chave dependa diretamente da chave, e de nada além dela.

A solução é separar cada coisa que tem vida própria em sua própria tabela:

CREATE TABLE planeta (
  nome_planeta VARCHAR(60) PRIMARY KEY,
  capital_planeta VARCHAR(60) NOT NULL
);

CREATE TABLE embaixador (
  nome_embaixador VARCHAR(80) PRIMARY KEY,
  email_embaixador VARCHAR(120) NOT NULL UNIQUE
);

CREATE TABLE visita_diplomatica (
  id_visita INT PRIMARY KEY AUTO_INCREMENT,
  nome_planeta VARCHAR(60) NOT NULL,
  nome_embaixador VARCHAR(80) NOT NULL,
  data_visita DATE NOT NULL,
  FOREIGN KEY (nome_planeta) REFERENCES planeta(nome_planeta),
  FOREIGN KEY (nome_embaixador) REFERENCES embaixador(nome_embaixador)
);

Agora: cadastrar um planeta não exige mais inventar uma visita; atualizar o e-mail de um embaixador é um único UPDATE, em uma única linha; e remover uma visita não apaga mais informação nenhuma sobre o planeta ou o embaixador. As três anomalias do início desapareceram.

6. Passo a passo para normalizar

  1. Identifiquem as dependências funcionais.

    Para cada atributo, perguntem: "de qual coluna (ou conjunto de colunas) esse valor realmente depende?"

  2. Garantam atomicidade (1FN).

    Nenhuma célula pode guardar mais de um valor; nenhum grupo de colunas pode se repetir.

  3. Procurem dependências parciais (2FN).

    Só relevante quando a chave é composta: todo atributo precisa depender da chave inteira.

  4. Procurem dependências transitivas (3FN).

    Todo atributo não-chave precisa depender diretamente da chave, nunca de outro atributo não-chave.

  5. Separem o que tem vida própria em tabelas próprias.

    Se um conjunto de atributos descreve algo que existe independente da linha atual (como um planeta ou um embaixador), ele provavelmente merece sua própria tabela.

🤔 Confira se entendeu

Por que capital_planeta → nome_planeta é uma dependência transitiva em relação a id_visita?

Porque id_visita determina nome_planeta, e nome_planeta determina capital_planeta — então capital_planeta só depende de id_visita de forma indireta, passando por nome_planeta, e não diretamente.

A tabela visita_idioma, com chave composta (id_visita, idioma), viola a 2FN?

Não, porque ela não tem nenhum atributo além dos que compõem a própria chave primária — não há nada que possa depender parcialmente da chave.
