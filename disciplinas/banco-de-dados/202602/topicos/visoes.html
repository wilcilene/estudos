Visões

Visões (Views)

Até aqui, vocês sempre consultaram as tabelas diretamente. Mas e se eu quiser mostrar só uma parte dos dados para alguém, sem dar acesso à tabela inteira — e sem copiar os dados para outro lugar? É para isso que existem as views. Vamos explorar a Biblioteca Intergaláctica e seus acervos restritos por nível de acesso.

O que vocês vão aprender aqui

  • Entender o que é uma view e por que ela não guarda dados próprios.
  • Criar views com CREATE VIEW.
  • Diferenciar views comuns de views atualizáveis.
  • Usar views para segurança (restringir colunas/linhas) e para abstração (simplificar consultas repetidas).

1. A Biblioteca Intergaláctica

📚 Biblioteca Intergaláctica

A biblioteca guarda registros de todas as espécies catalogadas da galáxia. Mas nem todo visitante pode ver tudo: há dados confidenciais (coordenadas de planetas-sede, por exemplo) que só a diretoria pode consultar.

CREATE TABLE especie (
  id_especie INT PRIMARY KEY AUTO_INCREMENT,
  nome_especie VARCHAR(80) NOT NULL,
  classificacao VARCHAR(40),
  planeta_sede VARCHAR(80),
  coordenadas_sede VARCHAR(60),
  nivel_ameaca VARCHAR(20)
);

Visitantes comuns podem consultar nome, classificação e nível de ameaça. Mas planeta_sede e coordenadas_sede são informações sigilosas — só a diretoria da biblioteca pode vê-las.

2. Criando uma view pública

Em vez de dar acesso à tabela especie inteira para os visitantes, eu crio uma view que já esconde as colunas sigilosas:

CREATE VIEW vw_especie_publica AS
SELECT id_especie, nome_especie, classificacao, nivel_ameaca
FROM especie;
Linha a linha: a view pública
TrechoO que significa
CREATE VIEW vw_especie_publica AS Cria uma view chamada vw_especie_publica. A partir daqui, o que vem é a consulta que define essa view.
SELECT id_especie, nome_especie, ... A view só mostra essas quatro colunas — planeta_sede e coordenadas_sede nunca aparecem para quem consulta a view.
FROM especie; A view busca os dados na tabela real especie, mas ninguém que usa a view precisa saber disso.

Agora, qualquer visitante pode consultar a view como se fosse uma tabela comum:

SELECT * FROM vw_especie_publica WHERE nivel_ameaca = 'baixo';

Conceito: a view não guarda dados

Uma view não duplica os dados da tabela. Ela é, na prática, uma consulta SELECT salva com um nome. Toda vez que alguém consulta a view, o SGBD executa essa consulta de novo contra a tabela real. Se a tabela especie mudar, a view reflete a mudança imediatamente — porque ela não tem dados próprios para ficar desatualizados.

3. Views para segurança: restringindo linhas também

Views não restringem só colunas — também podem restringir linhas. Imagine que visitantes comuns não devem ver nenhuma espécie classificada como alto risco, nem o próprio nível de ameaça dela:

CREATE VIEW vw_especie_segura AS
SELECT id_especie, nome_especie, classificacao
FROM especie
WHERE nivel_ameaca <> 'alto';

Quem consulta vw_especie_segura nunca vê as espécies de alto risco — elas simplesmente não existem do ponto de vista dessa view. É uma forma de aplicar regras de negócio de acesso diretamente no banco, sem depender só da aplicação para filtrar.

4. Views atualizáveis

Algumas views aceitam INSERT, UPDATE e DELETE como se fossem tabelas — são as views atualizáveis. Isso só funciona quando a view vem de uma única tabela, sem agregações, GROUP BY, DISTINCT ou junções complexas, de forma que o SGBD consiga traduzir a alteração de volta para a tabela original sem ambiguidade.

UPDATE vw_especie_publica
SET classificacao = 'reclassificada'
WHERE id_especie = 7;

Como vw_especie_publica vem de uma tabela só e não tem agregação, essa alteração é traduzida pelo SGBD para um UPDATE real na tabela especie.

🚫 Quando a view deixa de ser atualizável

Se a view tiver GROUP BY, funções agregadas (COUNT, SUM...), DISTINCT, uniões de várias tabelas sem chave clara ou subconsultas, o SGBD não consegue decidir de forma única qual linha da tabela original cada linha da view representa — e a view passa a ser somente para leitura.

5. Views para abstração: simplificando o que se repete

Suponha que, toda semana, a diretoria precisa da contagem de espécies catalogadas por classificação. Em vez de repetir essa consulta com GROUP BY todas as vezes, eu salvo a lógica em uma view:

CREATE VIEW vw_resumo_classificacao AS
SELECT classificacao, COUNT(*) AS total_especies
FROM especie
GROUP BY classificacao;

A partir daqui, basta consultar SELECT * FROM vw_resumo_classificacao; sempre que precisar do resumo — a lógica de agrupamento fica escondida dentro da view, e quem consulta nem precisa saber que existe um GROUP BY por trás. Essa view, por ter agregação, é somente para leitura.

🤔 Confira se entendeu

Por que uma view não fica "desatualizada" quando a tabela original muda?

Porque a view não guarda dados próprios — ela é uma consulta salva, executada de novo contra a tabela real a cada vez que é consultada.

A view vw_resumo_classificacao aceita UPDATE? Por quê?

Não. Ela usa GROUP BY e uma função agregada (COUNT), então o SGBD não conseguiria traduzir uma alteração na view de volta para uma linha específica da tabela especie.
