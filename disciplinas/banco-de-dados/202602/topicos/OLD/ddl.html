DDL: criando um banco para clínica veterinária

Nesta aula prática, você utilizará o MySQL Workbench para construir a estrutura de um sistema de agendamentos veterinários. O roteiro apresenta o que executar, em que ordem executar, por que cada linha de código existe e como verificar o resultado de cada etapa.

Você já programa e já conhece lógica, tipos de dados e estruturas de repetição — mas talvez esta seja a primeira vez que crie um banco de dados do zero. Por isso, sempre que um comando SQL aparecer, ele virá acompanhado de uma tabela explicando o que cada trecho faz, e sempre que um conceito novo surgir, ele será relacionado a algo que você já conhece da programação.

Objetivos de aprendizagem

  • Utilizar o MySQL Workbench para executar scripts SQL.
  • Explicar o papel da DDL na definição da estrutura do banco.
  • Reconhecer o significado de cada palavra-chave usada em um CREATE TABLE.
  • Criar tabelas com tipos de dados, chaves e restrições.
  • Representar relacionamentos 1:N e N:M.
  • Inspecionar tabelas e interpretar mensagens de erro.
  • Organizar um script SQL reprodutível e documentado.

0. Vocabulário essencial antes de começar

Estes são os termos que vão aparecer repetidamente no restante da aula. Leia uma vez agora e volte aqui sempre que precisar — não é necessário decorar.

Banco de dados (database)
Um espaço isolado no servidor MySQL onde ficam guardadas as tabelas de um sistema. Um mesmo servidor MySQL pode hospedar vários bancos, do mesmo jeito que um sistema operacional guarda várias pastas de projetos diferentes.
Tabela
Uma estrutura que guarda dados de um mesmo tipo de "coisa" (pets, veterinários, consultas). Para quem programa, pense na tabela como a definição de uma classe ou de um struct: ela descreve quais campos existem, mas ainda não é um dado concreto.
Coluna (ou atributo/campo)
Cada informação que a tabela guarda, com um nome e um tipo fixo — equivalente a um atributo/propriedade de uma classe, como String nome ou int idade.
Linha (ou registro/tupla)
Um valor concreto guardado na tabela, com um valor para cada coluna — equivalente a uma instância/objeto criado a partir da classe.
Chave primária (PRIMARY KEY / PK)
A coluna (ou conjunto de colunas) que identifica cada linha de forma única, sem repetição. É parecida com o id que você provavelmente já usou em APIs REST ou com uma chave de mapa/dicionário: não pode haver duas linhas com a mesma chave.
Chave estrangeira (FOREIGN KEY / FK)
Uma coluna que guarda o valor da chave primária de outra tabela, criando uma ligação entre elas. É o equivalente relacional a guardar uma referência/ponteiro para outro objeto, só que validado pelo próprio banco de dados.
Restrição (constraint)
Uma regra que o banco passa a impor automaticamente sobre os dados (obrigatoriedade, unicidade, valor padrão, faixa de valores válidos). É como uma validação que, em vez de ficar só no seu código, também é garantida pelo banco — mesmo que outro sistema grave dados diretamente nele.
AUTO_INCREMENT
Instrui o MySQL a gerar automaticamente o próximo número inteiro disponível para a coluna sempre que uma nova linha é inserida — parecido com um contador global que o próprio banco mantém.
Charset e collation
Charset define quais caracteres podem ser armazenados (o utf8mb4 aceita acentos, cedilha e até emojis). Collation define como o banco compara e ordena texto (se diferencia maiúsculas de minúsculas, se ignora acentos na ordenação, etc.).
DDL, DML e DQL
DDL (Data Definition Language) cria e altera estruturas: CREATE, ALTER, DROP. DML (Data Manipulation Language) manipula os dados dentro das estruturas: INSERT, UPDATE, DELETE. DQL (Data Query Language) consulta dados: SELECT. Nesta aula você trabalha só com DDL. O SELECT é tecnicamente DQL, mas costuma ser estudado junto com DML no próximo tópico, porque, na prática, você só consegue confirmar se um INSERT, UPDATE ou DELETE funcionou consultando os dados logo em seguida — as duas coisas andam juntas no dia a dia, mesmo sendo categorias formalmente diferentes.
Índice (INDEX)
Uma estrutura auxiliar que o MySQL mantém para encontrar linhas mais rápido, sem precisar ler a tabela inteira — o mesmo papel do índice de um livro. Toda PRIMARY KEY e toda coluna UNIQUE já ganham um índice automaticamente; é possível criar índices extras depois, com CREATE INDEX.
Integridade referencial
A garantia de que toda chave estrangeira aponta para um registro que realmente existe — nunca uma "referência quebrada". É exatamente o que as cláusulas FOREIGN KEY, ON UPDATE e ON DELETE desta aula existem para manter, mesmo quando dados são alterados ou apagados.

1. DDL e o MySQL Workbench

DDL é o conjunto de comandos SQL utilizado para criar, modificar e remover estruturas do banco de dados. Neste roteiro, você usará principalmente CREATE DATABASE, CREATE TABLE e restrições de integridade.

O MySQL Workbench será o ambiente de trabalho. Ele permite abrir uma conexão com o servidor MySQL, escrever comandos no SQL Editor, executar scripts por seleção ou por bloco, visualizar mensagens e consultar a estrutura criada.

Para quem já programa

O Workbench funciona como uma mistura de terminal + IDE apenas para banco de dados: o SQL Editor é onde você escreve o "código" (SQL), o Output é o equivalente ao console/terminal onde aparecem erros e mensagens de sucesso, e o Navigator é como o explorador de arquivos do seu editor de código, só que mostrando bancos, tabelas e colunas em vez de pastas e arquivos.

Elementos do MySQL Workbench usados nesta aula
Elemento Função
MySQL Connections Lista e abre conexões com servidores MySQL.
SQL Editor Área em que o script SQL é digitado e executado.
Navigator / Schemas Exibe bancos, tabelas, views e outros objetos da conexão.
Action Output Exibe mensagens de sucesso, avisos e erros da execução.

2. Preparar o MySQL Workbench

Antes de escrever comandos, confirme que o Workbench está conectado ao servidor MySQL disponibilizado no laboratório. Se você precisa instalar e configurar o ambiente clique aqui.

  1. Abra o MySQL Workbench no computador.
  2. Na tela inicial, localize a conexão indicada pelo professor.
  3. Dê duplo clique na conexão para abrir o SQL Editor.
  4. Aguarde o carregamento do painel Navigator e da área de edição.
  5. Crie uma nova aba SQL pelo botão de nova consulta, se necessário.
  6. Salve imediatamente o arquivo pelo menu File → Save Script As....
  7. Use o nome 01_clinica_veterinaria_ddl.sql.

Importante: o Workbench é o cliente. O banco de dados fica no servidor MySQL. Abrir o Workbench não cria automaticamente um banco; é necessário executar os comandos SQL na conexão correta. É a mesma lógica de um cliente HTTP (como o Postman) versus a API que ele consome: a ferramenta não é o serviço, apenas fala com ele.

3. Cenário da clínica

O banco clinica_veterinaria_db armazenará dados necessários para organizar agendamentos e atendimentos de uma clínica veterinária.

Conceito: de entidade a tabela

Cada linha da tabela abaixo é uma entidade do sistema — um "tipo de coisa" que precisa ser guardada. No próximo passo, cada entidade vira uma tabela, cada característica dela vira uma coluna, e cada relação entre entidades vira uma chave estrangeira (para relações 1:N) ou uma tabela extra (para relações N:M). É o mesmo raciocínio de modelagem que você já usa ao desenhar classes de domínio antes de escrever código.

Entidades do sistema
Entidade Finalidade Relações principais
Responsável Registra a pessoa que responde pelo pet. Um responsável pode ter vários pets.
Pet Registra o animal atendido. Cada pet possui um responsável principal.
Veterinário Registra profissionais da clínica. Um veterinário pode atender várias consultas.
Especialidade Classifica áreas de atuação. Relacionamento N:M com veterinário.
Tipo de atendimento Define serviço, duração e valor base. Um tipo pode ser usado em muitas consultas.
Consulta Registra o agendamento e o atendimento. Relaciona pet, veterinário e tipo de atendimento.
Procedimento Registra procedimentos oferecidos. Relacionamento N:M com consulta.

4. Criar e selecionar o banco

Digite o script abaixo no SQL Editor. O comando CREATE DATABASE cria o banco; o comando USE seleciona o banco para os próximos comandos.

CREATE DATABASE IF NOT EXISTS clinica_veterinaria_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE clinica_veterinaria_db;
Linha a linha: criação e seleção do banco
Trecho O que significa
CREATE DATABASE Comando DDL que cria um novo banco de dados (um novo "espaço" isolado) dentro do servidor MySQL.
IF NOT EXISTS Faz o comando ser idempotente: se o banco já existir, o MySQL não tenta criá-lo de novo e não gera erro. Sem essa cláusula, executar o script duas vezes causaria o erro "database exists".
clinica_veterinaria_db Nome escolhido para o banco. É um identificador, como o nome de um projeto ou de um pacote no seu código.
CHARACTER SET utf8mb4 Define o conjunto de caracteres aceito pelo banco. utf8mb4 é a variante completa do UTF-8 no MySQL, necessária para acentuação e emojis (o utf8 "antigo" do MySQL não suporta todos os caracteres Unicode).
COLLATE utf8mb4_unicode_ci Define a regra de comparação/ordenação de texto. O sufixo _ci significa case-insensitive: "Rex" e "rex" são tratados como iguais em comparações e buscas.
; Ponto e vírgula: encerra a instrução SQL, do mesmo jeito que encerraria uma instrução em Java, C# ou JavaScript com ;.
USE clinica_veterinaria_db; Não cria nada — apenas diz ao MySQL "a partir de agora, todo comando sem nome de banco explícito se aplica a este banco". Equivale a fazer um cd para dentro da pasta do projeto antes de rodar comandos nela.

5. Escolher tipos e restrições

Antes de criar as tabelas, relacione cada informação do cenário a um tipo de dado e a uma regra de armazenamento.

Tipos utilizados no banco veterinário
Tipo Uso Exemplo
INT Identificadores e números inteiros. id_pet, duracao_minutos
VARCHAR(n) Texto com limite de tamanho. nome, status
CHAR(n) Texto de tamanho fixo. CPF sem pontuação, com 11 caracteres.
DATE Data sem horário. data_nascimento
DATETIME Data e hora. data_hora da consulta.
DECIMAL(p,s) Valores numéricos exatos. peso_kg, valor_base
BOOLEAN Estado verdadeiro/falso. ativo

Para quem já programa

Pense nesses tipos como equivalentes aos tipos que você já usa: INT ≈ int; VARCHAR(n) ≈ String com tamanho máximo; BOOLEAN ≈ boolean/bool; DATE/DATETIME ≈ LocalDate/LocalDateTime. A diferença mais importante é o DECIMAL(p,s): diferente de float/double, ele guarda o número exato (sem erro de arredondamento binário), por isso é o tipo correto para dinheiro e peso — p é o total de dígitos e s quantos ficam depois da vírgula. Em DECIMAL(10,2), por exemplo, cabem até 8 dígitos antes da vírgula e 2 depois.

Além do tipo, cada coluna pode receber restrições que o banco passa a validar sozinho:

NOT NULL
O valor é obrigatório: o MySQL recusa qualquer INSERT ou UPDATE que deixe essa coluna vazia.
UNIQUE
Impede que duas linhas tenham o mesmo valor nessa coluna, mesmo que a coluna não seja a chave primária.
DEFAULT valor
Se nenhum valor for informado ao inserir a linha, o banco usa automaticamente o valor padrão indicado.
CHECK (condição)
Só aceita a linha se a condição for verdadeira. É uma validação de domínio feita pelo próprio banco, útil mesmo quando vários sistemas diferentes gravam na mesma tabela.
PRIMARY KEY
Marca a coluna (ou conjunto de colunas) como identificador único e obrigatório da linha.
FOREIGN KEY
Conecta uma coluna desta tabela à chave primária de outra tabela, garantindo que só existam referências válidas.

6. Criar as tabelas independentes

Crie primeiro as tabelas que não dependem de chaves estrangeiras. Essa ordem é importante: as tabelas referenciadas precisam existir antes de serem usadas como destino de uma chave estrangeira — o MySQL não consegue criar uma referência para algo que ainda não existe, do mesmo jeito que você não pode importar uma classe que ainda não foi criada.

CREATE TABLE responsavel (
  id_responsavel INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(120) NOT NULL,
  cpf CHAR(11) NOT NULL UNIQUE,
  telefone VARCHAR(20) NOT NULL,
  email VARCHAR(120) UNIQUE
);

CREATE TABLE veterinario (
  id_veterinario INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(120) NOT NULL,
  crmv VARCHAR(20) NOT NULL UNIQUE,
  telefone VARCHAR(20) NOT NULL,
  email VARCHAR(120) NOT NULL UNIQUE,
  ativo BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE especialidade (
  id_especialidade INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(80) NOT NULL UNIQUE,
  descricao VARCHAR(255)
);

CREATE TABLE tipo_atendimento (
  id_tipo_atendimento INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(80) NOT NULL UNIQUE,
  duracao_minutos INT NOT NULL,
  valor_base DECIMAL(10,2) NOT NULL,
  ativo BOOLEAN NOT NULL DEFAULT TRUE,

  CONSTRAINT chk_tipo_atendimento_duracao
    CHECK (duracao_minutos > 0),

  CONSTRAINT chk_tipo_atendimento_valor
    CHECK (valor_base >= 0)
);

Conceito: a "forma" geral de um CREATE TABLE

Todo comando segue o mesmo esqueleto: CREATE TABLE nome_da_tabela ( lista_de_colunas_separadas_por_vírgula, restrições_extras );. Cada linha dentro dos parênteses descreve uma coluna com o formato nome_da_coluna TIPO restrições. A vírgula separa itens, igual a uma lista de parâmetros em uma função — e por isso o último item antes do ) nunca tem vírgula.

7. Criar PET e sua chave estrangeira

Agora crie a tabela pet. A coluna id_responsavel representa o lado N de uma relação 1:N: um responsável pode estar associado a vários pets.

CREATE TABLE pet (
  id_pet INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(80) NOT NULL,
  especie VARCHAR(40) NOT NULL,
  raca VARCHAR(80),
  sexo CHAR(1) NOT NULL,
  data_nascimento DATE,
  peso_kg DECIMAL(5,2),
  observacoes VARCHAR(500),
  id_responsavel INT NOT NULL,

  CONSTRAINT chk_pet_sexo
    CHECK (sexo IN ('M', 'F')),

  CONSTRAINT chk_pet_peso
    CHECK (peso_kg IS NULL OR peso_kg > 0),

  CONSTRAINT fk_pet_responsavel
    FOREIGN KEY (id_responsavel)
    REFERENCES responsavel(id_responsavel)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);
Linha a linha: CREATE TABLE pet
Trecho O que significa
CREATE TABLE pet ( Inicia a tabela pet.
id_pet INT PRIMARY KEY AUTO_INCREMENT, Identificador único e autogerado do pet.
nome VARCHAR(80) NOT NULL, Nome do pet, obrigatório.
especie VARCHAR(40) NOT NULL, Espécie (cão, gato, ave...), obrigatória. Foi usado texto livre, e não uma lista fixa, porque a clínica pode atender espécies variadas.
raca VARCHAR(80), Raça do pet, opcional (sem NOT NULL) — nem todo pet tem raça definida.
sexo CHAR(1) NOT NULL, Um único caractere obrigatório para o sexo do animal. Usa CHAR(1), e não VARCHAR(1), porque o tamanho é sempre exatamente 1, e CHAR é ligeiramente mais eficiente para tamanho fixo.
data_nascimento DATE, Data de nascimento, opcional — pode não ser conhecida no cadastro.
peso_kg DECIMAL(5,2), Peso em quilos, opcional, com até 5 dígitos no total e 2 depois da vírgula (até 999,99 kg).
observacoes VARCHAR(500), Texto livre opcional e mais longo, para anotações gerais.
id_responsavel INT NOT NULL, Coluna que vai guardar o id_responsavel de algum registro da tabela responsavel. É obrigatória porque, no cenário desta clínica, todo pet precisa ter um responsável. Sozinha, ainda é só uma coluna INT comum — é a FOREIGN KEY mais abaixo que transforma esse número em uma referência validada.
CONSTRAINT chk_pet_sexo Nomeia a restrição de validação do sexo.
CHECK (sexo IN ('M', 'F')), Só aceita a linha se sexo for exatamente 'M' ou 'F'. É o equivalente, no banco, a restringir os valores possíveis de uma enum no seu código — só que a validação acontece no servidor de dados, não na aplicação.
CONSTRAINT chk_pet_peso Nomeia a restrição de validação do peso.
CHECK (peso_kg IS NULL OR peso_kg > 0), Como o peso é opcional, a condição precisa aceitar tanto "não informado" (IS NULL) quanto "informado e maior que zero". Sem o IS NULL, o CHECK rejeitaria também os pets sem peso cadastrado.
CONSTRAINT fk_pet_responsavel Nomeia a chave estrangeira que vem a seguir, seguindo o padrão fk_ (de foreign key) + tabela + tabela referenciada.
FOREIGN KEY (id_responsavel) Declara que a coluna id_responsavel, definida acima, é uma chave estrangeira.
REFERENCES responsavel(id_responsavel) Diz a qual tabela e a qual coluna essa chave estrangeira aponta: a coluna id_responsavel da tabela responsavel. A partir de agora, o MySQL rejeita qualquer pet cujo id_responsavel não exista na tabela responsavel.
ON UPDATE CASCADE Se o id_responsavel de um responsável for alterado na tabela responsavel, o MySQL atualiza automaticamente esse valor em todos os pets relacionados, mantendo a ligação íntegra.
ON DELETE RESTRICT Impede a exclusão de um responsável enquanto ele ainda tiver pets cadastrados — o comando DELETE falha com erro em vez de apagar (ou deixar órfão) o pet. Isso protege o histórico da clínica contra exclusões acidentais.
); Fecha e encerra o comando.

Conceito: por que pet só pode ser criada depois de responsavel?

Ao declarar REFERENCES responsavel(id_responsavel), o MySQL precisa conferir se a tabela responsavel e a coluna id_responsavel realmente existem no momento em que o CREATE TABLE pet é executado. Se você tentasse criar pet antes de responsavel, o comando falharia, porque não é possível referenciar algo que ainda não existe — é o mesmo motivo pelo qual você não consegue importar uma classe de um arquivo que ainda não foi criado.

Para conferir a estrutura, execute:

DESCRIBE pet;
SHOW CREATE TABLE pet;
Linha a linha: comandos de inspeção
Trecho O que significa
DESCRIBE pet; Lista as colunas da tabela pet, seus tipos, se aceitam NULL, quais são chave e quais têm valor padrão — um resumo rápido da estrutura.
SHOW CREATE TABLE pet; Mostra o comando CREATE TABLE equivalente exatamente como o MySQL o entendeu e guardou, incluindo nomes de constraints — útil para conferir se tudo foi criado como esperado.

8. Criar a relação N:M entre veterinário e especialidade

Um veterinário pode possuir várias especialidades, e uma especialidade pode pertencer a vários veterinários. Para essa relação N:M, crie uma tabela associativa.

Conceito: por que uma relação N:M precisa de uma tabela extra?

Uma chave estrangeira só consegue guardar uma referência por linha, o que resolve relações 1:N (um pet tem um único responsável). Numa relação N:M, cada lado pode se associar a vários registros do outro lado ao mesmo tempo, então nenhuma das duas tabelas originais consegue guardar isso sozinha. A solução é criar uma tabela associativa (também chamada de tabela de junção): cada linha dela representa um par válido "este veterinário tem esta especialidade", e ela guarda uma chave estrangeira para cada lado da relação.

CREATE TABLE veterinario_especialidade (
  id_veterinario INT NOT NULL,
  id_especialidade INT NOT NULL,

  PRIMARY KEY (id_veterinario, id_especialidade),

  CONSTRAINT fk_vet_esp_veterinario
    FOREIGN KEY (id_veterinario)
    REFERENCES veterinario(id_veterinario)
    ON UPDATE CASCADE
    ON DELETE RESTRICT,

  CONSTRAINT fk_vet_esp_especialidade
    FOREIGN KEY (id_especialidade)
    REFERENCES especialidade(id_especialidade)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);

10. Criar procedimentos e a relação N:M com consulta

Uma consulta pode possuir vários procedimentos. Um procedimento, como vacinação ou microchipagem, pode ser realizado em várias consultas. Essa relação N:M exige uma tabela própria.

CREATE TABLE procedimento (
  id_procedimento INT PRIMARY KEY AUTO_INCREMENT,
  nome VARCHAR(100) NOT NULL UNIQUE,
  descricao VARCHAR(500),
  valor_base DECIMAL(10,2) NOT NULL,

  CONSTRAINT chk_procedimento_valor
    CHECK (valor_base >= 0)
);

CREATE TABLE consulta_procedimento (
  id_consulta INT NOT NULL,
  id_procedimento INT NOT NULL,
  quantidade INT NOT NULL DEFAULT 1,
  valor_cobrado DECIMAL(10,2) NOT NULL,
  observacao VARCHAR(500),

  PRIMARY KEY (id_consulta, id_procedimento),

  CONSTRAINT chk_consulta_procedimento_quantidade
    CHECK (quantidade > 0),

  CONSTRAINT chk_consulta_procedimento_valor
    CHECK (valor_cobrado >= 0),

  CONSTRAINT fk_consulta_procedimento_consulta
    FOREIGN KEY (id_consulta)
    REFERENCES consulta(id_consulta)
    ON UPDATE CASCADE
    ON DELETE CASCADE,

  CONSTRAINT fk_consulta_procedimento_procedimento
    FOREIGN KEY (id_procedimento)
    REFERENCES procedimento(id_procedimento)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
);

Conceito: atributos que pertencem ao relacionamento, não às entidades

Repare que quantidade, valor_cobrado e observacao não fazem sentido nem em consulta nem em procedimento isoladamente: eles só existem porque este procedimento foi feito nesta consulta. Por isso ficam na tabela associativa, e não em nenhuma das duas tabelas originais. É comum uma tabela N:M carregar dados próprios do vínculo, além das duas chaves estrangeiras.

Linha a linha: CREATE TABLE consulta_procedimento
Trecho O que significa

id_procedimento INT NOT NULL, Vai referenciar um procedimento; obrigatória.

valor_cobrado DECIMAL(10,2) NOT NULL, Valor efetivamente cobrado por este procedimento nesta consulta específica; obrigatório (diferente da tabela consulta, onde o valor geral podia ficar em aberto).
observacao VARCHAR(500), Anotação opcional sobre este procedimento nesta consulta.

CONSTRAINT chk_consulta_procedimento_valor

Para quem já programa

CASCADE e RESTRICT são escolhas de design, não uma regra fixa do MySQL — parecido com decidir, ao apagar um objeto pai na sua aplicação, se os objetos filhos devem ser apagados junto ou se a operação deve ser bloqueada. Aqui, apagar uma consulta arrasta seus procedimentos vinculados (CASCADE), mas apagar um procedimento do catálogo é bloqueado se ele já foi usado (RESTRICT), porque o catálogo de procedimentos deve ser mais estável que o histórico de uma consulta específica.

Os atributos quantidade, valor_cobrado e observacao pertencem ao relacionamento, pois descrevem o procedimento dentro de uma consulta específica.

12. Script consolidado

Depois de testar cada etapa, mantenha uma versão completa do script. O bloco abaixo pode ser salvo e executado novamente em um banco vazio, desde que as tabelas ainda não existam.

Execute o bloco inteiro somente depois de compreender a ordem de criação. Tabelas pai vêm antes das tabelas filhas porque as chaves estrangeiras dependem delas.

Conceito: mapa de dependências entre as tabelas

Antes de rodar o script completo, é útil visualizar por que a ordem abaixo é a única que funciona sem erro:

  1. responsavel, veterinario, especialidade, tipo_atendimento — não têm chave estrangeira, podem ser criadas em qualquer ordem entre si.
  2. pet — depende de responsavel já existir.
  3. veterinario_especialidade — depende de veterinario e especialidade.
  4. consulta — depende de pet, veterinario e tipo_atendimento.
  5. procedimento — não tem chave estrangeira, mas precisa existir antes do próximo item.
  6. consulta_procedimento — depende de consulta e procedimento.

Essa lista é, na prática, uma ordenação topológica das dependências — o mesmo tipo de problema que aparece ao resolver a ordem de inicialização de módulos com dependências entre si no código.

13. Problemas frequentes no Workbench

Como investigar problemas comuns
Situação Causa provável Como investigar
A instrução é executada, mas a tabela não aparece. O schema não foi atualizado no Navigator ou a tabela foi criada em outro banco. Execute SELECT DATABASE(); e atualize Schemas.
Erro ao criar uma chave estrangeira. A tabela pai não existe, os tipos não coincidem ou a coluna referenciada não é chave. Verifique a ordem dos comandos, tipos e resultado de SHOW CREATE TABLE.
Erro de sintaxe. Vírgula, parêntese ou palavra-chave incorreta. Leia a linha destacada no Output e execute o bloco em partes menores.
Erro ao remover registro relacionado. ON DELETE RESTRICT protege a integridade referencial. Verifique quais registros dependentes ainda existem antes de excluir.

Para quem já programa

Esses erros de banco cumprem o mesmo papel que exceções em tempo de execução no seu código: eles não são "coisas que deram errado com o programa", são a própria camada de dados recusando ativamente uma operação que quebraria uma regra de negócio (como excluir um responsável que ainda tem pets). Ler a mensagem completa no Output — e não só o código do erro — costuma indicar exatamente qual constraint foi violada.
