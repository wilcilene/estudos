Normalização

BCNF: quando a 3FN ainda não é suficiente

A 3FN resolve a maioria dos problemas, mas existe um caso específico — chaves candidatas que se sobrepõem — em que uma tabela passa na 3FN e ainda assim guarda redundância. Vamos ver esse caso com a escala de operadores de uma usina de energia alienígena, e depois falar sobre o oposto: desnormalizar de propósito.

O que vocês vão aprender aqui

  • Entender a definição formal da BCNF.
  • Identificar uma tabela que está na 3FN mas viola a BCNF.
  • Decompor essa tabela para eliminar a anomalia.
  • Reconhecer quando desnormalizar de propósito é uma decisão válida.

1. O cenário: a escala da usina

⚡ Usina de energia alienígena

A usina tem vários setores (reatores de fusão, de antimatéria, de energia solar concentrada). Cada operador é certificado para trabalhar em um único setor — essa é uma regra rígida de segurança. A escala registra quem trabalha em qual turno.

Reparem que "Vex Orlan" aparece duas vezes, e "Fusão" é repetido nas duas linhas. Isso já é um cheiro de redundância — mas, como vamos ver, essa tabela passa tranquilamente pela 3FN.

2. Duas chaves candidatas que se sobrepõem

Essa tabela tem duas dependências funcionais importantes:

Dependências funcionais de escala_operacao
DependênciaEm palavras
(setor, turno) → operadorPara cada setor e turno, existe só um operador escalado.
operador → setorCada operador é certificado para um único setor — essa é a regra de negócio da usina.

Como operador → setor e (setor, turno) → operador, temos duas chaves candidatas: (operador, turno) e (setor, turno) — qualquer uma das duas identifica uma linha sozinha.

3. Por que ela passa na 3FN (e ainda assim incomoda)

A 3FN proíbe dependência transitiva de um atributo não-chave para outro atributo não-chave. Mas setor não é não-chave aqui — ele é um atributo primo, porque participa da chave candidata (setor, turno). Então a dependência operador → setor não quebra a regra da 3FN, mesmo sendo exatamente o tipo de redundância que a normalização existe para evitar.

Conceito: a definição da BCNF

Uma tabela está na Forma Normal de Boyce-Codd quando, para toda dependência funcional não trivial X → Y, X é uma superchave (ou seja, X sozinho já determina a linha inteira). A diferença para a 3FN é sutil, mas decisiva: a 3FN abre uma exceção quando Y é um atributo primo; a BCNF não abre exceção nenhuma.

Testando operador → setor contra essa régua: operador sozinho não é superchave (ele não determina turno). Logo, essa dependência viola a BCNF — mesmo a tabela estando na 3FN.

4. Decompondo para BCNF

CREATE TABLE operador_setor (
  operador VARCHAR(60) PRIMARY KEY,
  setor VARCHAR(40) NOT NULL
);

CREATE TABLE escala (
  operador VARCHAR(60) NOT NULL,
  turno VARCHAR(20) NOT NULL,
  PRIMARY KEY (operador, turno),
  FOREIGN KEY (operador) REFERENCES operador_setor(operador)
);

Agora o setor de cada operador é guardado uma única vez, em operador_setor; escala só registra quem trabalha em qual turno. Atualizar a certificação de um operador vira um UPDATE em uma única linha, não importa em quantos turnos ele trabalhe.

⚠️ O preço da decomposição em BCNF

Depois dessa decomposição, a regra "para cada setor e turno, só um operador" não é mais garantida automaticamente por uma PRIMARY KEY simples — ela passa a depender de uma consulta ou de uma lógica extra para ser verificada. Esse é um trade-off conhecido da BCNF: ela sempre elimina a redundância, mas nem sempre preserva, de forma direta, todas as dependências funcionais originais da tabela.

5. O caminho contrário: desnormalizar de propósito

Tudo o que vimos até aqui — nesta aula e na anterior — empurra na direção de mais tabelas, cada uma mais enxuta. Só que normalizar demais tem um custo: cada consulta que junta informações espalhadas em várias tabelas pequenas precisa de mais JOINs, e JOIN custa processamento.

Em sistemas com volume alto de leitura — um painel de monitoramento da usina que atualiza a cada segundo, por exemplo — às vezes vale a pena aceitar um pouco de redundância de propósito, para evitar juntar várias tabelas a toda hora:

CREATE TABLE leitura_painel (
  id_leitura INT PRIMARY KEY AUTO_INCREMENT,
  operador VARCHAR(60) NOT NULL,
  setor VARCHAR(40) NOT NULL,   -- redundante: já existe em operador_setor
  temperatura_c DECIMAL(6,2) NOT NULL,
  registrado_em DATETIME NOT NULL
);

Aqui, setor está duplicado de propósito dentro de leitura_painel para que o painel não precise fazer JOIN com operador_setor a cada atualização — uma escolha consciente de performance, não um erro de modelagem.

Conceito: desnormalização é uma decisão, não um acidente

Desnormalizar sem perceber — simplesmente nunca separar as tabelas direito — é um problema. Desnormalizar de propósito, depois de já ter um modelo normalizado e identificar um gargalo real de desempenho, é uma técnica legítima. A diferença é que, no segundo caso, alguém precisa assumir a responsabilidade de manter os dados duplicados sincronizados (por exemplo, atualizando leitura_painel sempre que operador_setor mudar).

🤔 Confira se entendeu

Por que operador → setor não viola a 3FN, mas viola a BCNF?

Porque setor é um atributo primo (participa da chave candidata (setor, turno)), e a 3FN só proíbe dependências transitivas entre atributos não-primos. A BCNF não abre essa exceção: basta operador não ser superchave para a dependência violar a regra.

Em que situação faz sentido desnormalizar de propósito?

Quando um sistema já normalizado apresenta um gargalo real de desempenho em consultas de leitura muito frequentes, e a equipe está disposta a manter a sincronização dos dados duplicados.
