Procedimentos armazenados e funções

Até agora, cada operação no banco era um comando SQL isolado, disparado pela aplicação. Hoje vamos ver como guardar uma rotina inteira dentro do próprio banco, para ser executada sempre do mesmo jeito, por qualquer aplicação que precisar dela. Bem-vindos à oficina de montagem de robôs, onde rotinas automatizadas cuidam de tarefas repetitivas.

O que vocês vão aprender aqui

  • Entender o que é um procedimento armazenado (stored procedure).
  • Criar e chamar procedimentos com parâmetros.
  • Criar uma função definida pelo usuário que retorna um valor.
  • Discutir quando colocar lógica no banco e quando deixá-la na aplicação.

1. A oficina de montagem de robôs

🔧 Oficina RoboForge

Toda vez que um robô é montado, a oficina precisa registrar a peça usada, baixar o estoque dessa peça e marcar o robô como "em montagem". São três passos, sempre na mesma ordem, repetidos para cada robô montado.

CREATE TABLE peca (
  id_peca INT PRIMARY KEY AUTO_INCREMENT,
  nome_peca VARCHAR(60) NOT NULL,
  estoque INT NOT NULL DEFAULT 0
);

CREATE TABLE robo (
  id_robo INT PRIMARY KEY AUTO_INCREMENT,
  modelo VARCHAR(60) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'planejado'
);

CREATE TABLE uso_peca (
  id_robo INT,
  id_peca INT,
  quantidade INT NOT NULL,
  PRIMARY KEY (id_robo, id_peca),
  FOREIGN KEY (id_robo) REFERENCES robo(id_robo),
  FOREIGN KEY (id_peca) REFERENCES peca(id_peca)
);

2. Criando um procedimento armazenado

Em vez de repetir os três comandos toda vez — na aplicação, em scripts diferentes, por pessoas diferentes — eu guardo a rotina inteira no banco, com o nome registrar_uso_peca:

DELIMITER //

CREATE PROCEDURE registrar_uso_peca (
  IN p_id_robo INT,
  IN p_id_peca INT,
  IN p_quantidade INT
)
BEGIN
  INSERT INTO uso_peca (id_robo, id_peca, quantidade)
  VALUES (p_id_robo, p_id_peca, p_quantidade);

  UPDATE peca
  SET estoque = estoque - p_quantidade
  WHERE id_peca = p_id_peca;

  UPDATE robo
  SET status = 'em montagem'
  WHERE id_robo = p_id_robo;
END //

DELIMITER ;
Linha a linha: o procedimento
TrechoO que significa
DELIMITER // Troca temporariamente o caractere que marca "fim de comando" de ; para //, porque o corpo do procedimento usa ; internamente e não queremos que o cliente SQL corte o comando no meio.
CREATE PROCEDURE registrar_uso_peca (...) Declara o procedimento e seus parâmetros de entrada: qual robô, qual peça e qual quantidade.
IN p_id_robo INT IN indica que o parâmetro só entra valores — o procedimento não devolve nada através dele. O prefixo p_ evita confusão com nomes de colunas.
BEGIN ... END Delimita o corpo do procedimento: tudo que está entre eles é executado em sequência, como um bloco único, toda vez que o procedimento é chamado.
INSERT ... UPDATE ... UPDATE ... Os três comandos que antes seriam repetidos manualmente agora vivem dentro da rotina, sempre executados juntos e na mesma ordem.
DELIMITER ; Devolve o delimitador padrão para ;, já que terminamos de declarar o procedimento.

Para usar o procedimento, basta chamá-lo com CALL:

CALL registrar_uso_peca(12, 5, 2);

Uma única chamada executa os três passos, sempre na mesma ordem, sem que quem está chamando precise saber os detalhes internos da rotina.

Conceito: por que não envolver isso em uma transação?

Reparem que os três comandos dentro do procedimento formam, na prática, uma operação que deveria ser tudo-ou-nada — exatamente o problema que vimos com START TRANSACTION/COMMIT/ROLLBACK. Em um cenário real, esse procedimento normalmente envolveria os três comandos em uma transação, para garantir que, se algo falhar no meio, nenhuma das três alterações fique de pé.

3. Funções definidas pelo usuário

Uma função é parecida com um procedimento, mas tem uma diferença importante: ela sempre retorna um valor e pode ser usada dentro de uma expressão, como em um SELECT. Vamos criar uma função que calcula quantos robôs já foram montados usando uma determinada peça:

DELIMITER //

CREATE FUNCTION total_robos_com_peca (p_id_peca INT)
RETURNS INT
DETERMINISTIC
BEGIN
  DECLARE total INT;

  SELECT COUNT(DISTINCT id_robo) INTO total
  FROM uso_peca
  WHERE id_peca = p_id_peca;

  RETURN total;
END //

DELIMITER ;
Linha a linha: a função
TrechoO que significa
RETURNS INT Declara que essa função sempre devolve um número inteiro.
DETERMINISTIC Avisa ao SGBD que, para os mesmos parâmetros de entrada, a função sempre devolve o mesmo resultado — isso permite que o SGBD otimize o uso da função.
DECLARE total INT; Cria uma variável local total, que só existe durante a execução da função.
SELECT ... INTO total ... Executa a consulta e guarda o resultado dentro da variável total, em vez de devolvê-lo diretamente como resultado de consulta.
RETURN total; Devolve o valor calculado para quem chamou a função.

Como a função devolve um valor, posso usá-la dentro de um SELECT comum:

SELECT nome_peca, total_robos_com_peca(id_peca) AS robos_usando
FROM peca;

4. Lógica no banco ou lógica na aplicação?

Nem toda regra precisa (ou deve) virar um procedimento armazenado. Vale pensar em dois critérios:

Quando colocar lógica no banco
Favorece o bancoFavorece a aplicação
Regra usada por várias aplicações diferentes acessando o mesmo banco. Regra específica de uma única aplicação, que pode mudar com frequência.
Operação que precisa de garantias fortes de atomicidade/consistência perto dos dados. Lógica de interface, validação de formulário, regras que dependem de serviços externos.
Rotina de manutenção/auditoria que deve rodar independente de quem está usando o sistema. Equipe prefere versionar e testar a lógica de negócio junto com o código da aplicação.

💡 Não existe resposta única

Essa é uma decisão de arquitetura, não uma regra fixa de SQL. Times diferentes fazem escolhas diferentes — o importante é vocês entenderem o que um procedimento armazenado pode fazer, para decidir conscientemente quando usar essa ferramenta.

🤔 Confira se entendeu

Qual é a principal diferença entre um procedimento armazenado e uma função definida pelo usuário?

A função sempre retorna um valor e pode ser usada dentro de uma expressão (como em um SELECT); o procedimento não precisa retornar nada e é executado com CALL, de forma isolada.

Por que usamos DELIMITER // antes de criar o procedimento registrar_uso_peca?

Porque o corpo do procedimento contém vários comandos terminados em ponto e vírgula. Trocar o delimitador evita que o cliente SQL interprete o primeiro ponto e vírgula interno como o fim do CREATE PROCEDURE.
