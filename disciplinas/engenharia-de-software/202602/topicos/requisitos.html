01 O que é um requisito?

Requisito é uma necessidade, condição, capacidade ou restrição que o software deve atender. Ele explica o que deve ser entregue e fornece uma base para análise, projeto, implementação, testes e aceitação.

Um bom requisito É claro, necessário, consistente, priorizado, rastreável, verificável e compreensível para pessoas técnicas e não técnicas.

02 Stakeholders: quem participa ou é afetado?

Stakeholders são pessoas, grupos ou instituições que usam, financiam, administram, aprovam, influenciam ou sofrem impacto do sistema. Identificá-los evita que necessidades importantes fiquem fora do projeto.

Papéis típicos em um levantamento de requisitos
Stakeholder Interesse Como contribuir no levantamento
Jogador Realizar partidas de maneira clara, correta e divertida. Descrever regras, decisões, dúvidas e dificuldades durante uma partida.
Cliente / Product Owner Priorizar valor e decidir o que será entregue. Definir objetivo, escopo, prioridade e aceite.
Equipe de desenvolvimento Construir solução viável, sustentável e testável. Identificar riscos, dependências, ambiguidades e restrições técnicas.
Professor / avaliador Verificar aprendizagem, coerência e evidências do processo. Revisar documentação, modelos, justificativas e resultados.

03 Requisitos funcionais, não funcionais e regras

Requisitos funcionais

Descrevem serviços, ações e comportamentos que o sistema deve oferecer.

Forma útil: "O sistema deve permitir/registrar/calcular..."

Requisitos não funcionais

Definem qualidades, restrições e condições sob as quais o sistema deve operar.

Forma útil: "O sistema deve responder em..., ser acessível..., proteger..."

Regras de negócio

Representam regras do domínio, independentemente da tecnologia.

Exemplo: apenas o jogador da vez pode realizar uma jogada.

Restrições

Limitam as opções de solução.

Exemplo: o projeto deverá usar Java e versionamento no GitHub.

04 Levantamento e especificação

Levantar requisitos é descobrir e organizar necessidades. Especificar é registrá-las de modo que possam ser compreendidas, revisadas, implementadas e testadas.

  1. Preparar: definir objetivo, escopo inicial, stakeholders e perguntas.
  2. Coletar: observar partidas, entrevistar jogadores, ler o manual, aplicar questionários e fazer brainstorming.
  3. Analisar: identificar ambiguidades, conflitos, dependências, regras e exceções.
  4. Especificar: registrar requisitos em tabela, histórias ou casos de uso.
  5. Validar: revisar com stakeholders e confirmar exemplos e critérios.
  6. Gerenciar: controlar versão, prioridade, mudanças e rastreabilidade.

06 Critérios de aceitação

Critérios de aceitação dizem como verificar objetivamente que um requisito foi atendido. Eles conectam requisito, testes e aceite do usuário.

Critério forte

"A partida só poderá iniciar com dois ou mais jogadores cadastrados e cada jogador deverá possuir um nome único."

Critério fraco

"A partida deve iniciar corretamente." A expressão "corretamente" é ambígua e não orienta teste.

Dica Para cada requisito, pergunte "como alguém demonstrará que isso foi atendido?" A resposta deve aparecer nos critérios de aceitação.

07 Como priorizar requisitos?

Priorizar é decidir o que será feito primeiro. A decisão deve considerar valor para o usuário, importância para o objetivo do projeto, urgência, riscos, dependências e esforço. A prioridade não é definitiva: ela deve ser revisada quando a equipe aprende algo novo ou quando o escopo muda.

Passo a passo

  1. Listar os requisitos e eliminar duplicidades.
  2. Identificar dependências: o que precisa existir antes de outro item funcionar?
  3. Discutir valor, risco, urgência e esforço com os stakeholders.
  4. Classificar os requisitos e registrar a justificativa.
  5. Selecionar os itens essenciais para o primeiro incremento.
  6. Revisar a ordem de prioridade a cada ciclo de trabalho.

Método MoSCoW

Categorias de priorização MoSCoW
Categoria Significado Exemplo
Must have Indispensável. Sem este requisito, o objetivo principal não é alcançado. No War, o sistema deve impedir que um jogador ataque fora do seu turno.
Should have Muito importante, mas o produto ainda funciona sem ele na primeira versão. No Banco Imobiliário, o sistema deve exibir histórico detalhado de transações.
Could have Agrega valor, mas pode ser feito apenas se houver tempo e capacidade. No Geomundo, o sistema pode exibir curiosidades extras após uma resposta.
Won't have now Foi considerado, porém ficará fora do escopo desta versão. Modo de partida on-line na primeira entrega.
Cuidado Se todos os requisitos forem classificados como Must have, a equipe não priorizou. Um item só é Must quando sua ausência inviabiliza o objetivo da versão atual.

08 Ferramentas para gerenciamento de requisitos

Ferramentas ajudam a registrar, versionar, priorizar, atribuir responsáveis e relacionar requisitos a diagramas, testes e código. A ferramenta não substitui a análise: ela organiza as decisões da equipe.

Opções de ferramentas e como usá-las
Ferramenta Uso resumido Exemplo simples
GitHub Issues + Projects Boa opção para equipes que já usam GitHub. Cada requisito pode ser uma Issue; o Project organiza prioridade, status e iteração. Criar a Issue "RF01 — Iniciar partida"; adicionar os campos Prioridade: Must, Status: Em análise e um link para o diagrama de casos de uso.
Azure Boards Organiza requisitos como itens de trabalho em backlog, quadro Kanban e sprints. Criar uma User Story "Como jogador, quero iniciar uma partida"; vinculá-la a tarefas, testes e bugs.
Jira + Confluence Combina rastreamento de itens com documentação colaborativa. Registrar "RF01" como tipo de item Requisito e documentar regras e decisões em uma página Confluence vinculada.
Planilha compartilhada Útil para levantamento inicial e discussão em sala, com baixa curva de aprendizagem. Criar colunas ID, tipo, descrição, prioridade, critérios de aceitação, responsável e status.

10 Atividade

Cada equipe deverá levantar os requisitos do projeto escolhido e priorizá-los.

11 Rastreabilidade em Java

O código não substitui a especificação, mas pode tornar regras e critérios verificáveis. O exemplo abaixo representa uma regra de turno e uma mensagem associada a um requisito.

Partida.java 
public final class Partida {
    private Jogador jogadorDaVez;

    // Rastreabilidade: RN01 - somente o jogador da vez pode jogar.
    public void realizarJogada(Jogador jogador, Jogada jogada) {
        if (!jogador.equals(jogadorDaVez)) {
            throw new IllegalStateException(
                "RN01: apenas o jogador da vez pode realizar uma jogada."
            );
        }

        jogada.executar();
    }
}

Ao criar testes, a equipe deve relacionar o nome do teste ou seu comentário ao requisito correspondente. Assim, uma mudança no requisito revela quais modelos, classes e testes precisam ser revisados.
