Uma receita de bolo tem passos em ordem, decisões (“se a massa estiver mole, acrescente farinha”) e tarefas que podem correr ao mesmo tempo (pré-aquecer o forno enquanto bate a massa). O diagrama de atividades é a forma padronizada de desenhar esse tipo de fluxo.

01 Para que serve o diagrama de atividades

O diagrama de atividades descreve um fluxo de trabalho: quais passos acontecem, em que ordem, onde há decisões, o que pode acontecer ao mesmo tempo e quem é responsável por cada parte. Ele lembra um fluxograma, mas vai além: representa paralelismo, responsabilidades (raias) e objetos que circulam entre os passos.

Use para modelar…Exemplo
Um processo de negócio, envolvendo pessoas e setoresDo pedido do cliente até a retirada no balcão.
O fluxo de um caso de usoOs passos de “realizar matrícula”, com as alternativas.
A lógica de um algoritmo ou métodoCalcular a situação de cada estudante.
Atividades × sequência

O diagrama de sequência foca em quem conversa com quem (objetos e mensagens). O de atividades foca em o que é feito e em que ordem (passos e decisões), sem se preocupar com qual objeto executa cada passo.

02 As peças do diagrama

São muitos símbolos, mas cada um tem uma função bem clara. Os seis primeiros resolvem a maior parte dos diagramas do dia a dia.

  • Nó inicial

    Círculo cheio. Onde a atividade começa. Normalmente há um só.

  • Ação

    Retângulo de cantos arredondados com um verbo no infinitivo: um passo que não será detalhado neste diagrama.

    Em código: uma instrução ou chamada de método.

  • Fluxo de controle

    Seta com ponta aberta: quando A termina, B pode começar.

    Em código: a instrução seguinte.

  • Decisão

    Losango com uma entrada e várias saídas, cada uma com uma guarda entre colchetes. Só um caminho é seguido.

    Em código: if / else, switch.

  • Junção (merge)

    O mesmo losango, agora com várias entradas e uma saída: reúne caminhos alternativos. Não espera por ninguém.

    Em código: o ponto depois do if/else.

  • Bifurcação (fork)

    Barra com uma entrada e várias saídas: todos os caminhos seguem em paralelo.

    Em código: tarefas simultâneas (threads).

  • União (join)

    Barra com várias entradas e uma saída: espera todos os caminhos paralelos chegarem.

    Em código: esperar as tarefas terminarem.

  • Final da atividade

    “Olho de boi”. Ao chegar aqui, toda a atividade termina — inclusive caminhos paralelos ainda em andamento.

    Em código: return do método.

  • Final de fluxo

    Círculo com X. Encerra apenas aquele caminho; o resto da atividade continua.

  • Nó de objeto

    Retângulo de cantos retos com o nome de um objeto ou dado que passa de uma ação para outra. Pode indicar o estado: Pedido [pago].

  • Partição (raia)

    Faixas que mostram quem é responsável por cada ação: pessoas, setores ou sistemas.

  • Enviar sinal

    Pentágono “apontando”: a atividade envia uma mensagem e segue sem esperar.

  • Aceitar evento

    Pentágono com entalhe: a atividade espera um evento chegar para continuar.

  • Evento de tempo

    Ampulheta: espera um tempo ou uma data. Ex.: cancelar o pedido se não for pago após 10 minutos.

Mesmo desenho, papéis diferentes

O losango serve tanto para decisão (uma entrada, várias saídas) quanto para junção (várias entradas, uma saída). A barra serve tanto para fork quanto para join. O que diferencia é o número de setas entrando e saindo.

03 Decisão × paralelismo: pense em fichas

A especificação da UML explica o comportamento do diagrama de atividades com a ideia de fichas (tokens) que percorrem as setas. O nó inicial coloca uma ficha no fluxo; uma ação só executa quando a ficha chega até ela; ao terminar, passa a ficha adiante.

  • Na decisão, a ficha segue pela única saída cuja guarda é verdadeira. As guardas devem ser mutuamente exclusivas e cobrir todos os casos — use [else] para o “caso contrário”.
  • No fork, a ficha é copiada para todas as saídas. No join, o fluxo só continua quando chegam fichas de todas as entradas.
  • O merge deixa passar cada ficha assim que ela chega. Por isso, nunca use merge para reunir caminhos paralelos: use join.

04 Exemplo 1: o diagrama de um algoritmo

Para aquecer, um exemplo pequeno ligado à classe Estudante da revisão de OO: para cada estudante, calcular a média e definir a situação — aprovado (média ≥ 6), exame (entre 4 e 6) ou reprovado (abaixo de 4).

Compare o diagrama com o código: cada símbolo tem uma tradução direta.

No diagramaNo código
Decisão com três guardasif / else if / else
Merge depois das três situaçõesA linha logo após o bloco if
Decisão [há mais estudantes] voltando para o merge do topoO laço for
Turma.java · o mesmo fluxo em Java
public void exibirSituacoes(List<Estudante> estudantes) {
    for (Estudante e : estudantes) {             // [há mais estudantes]
        double media = e.calcularMedia();         // Calcular média
        String situacao;
        if (media >= 6) {                          // [média ≥ 6]
            situacao = "aprovado";
        } else if (media >= 4) {                   // [4 ≤ média < 6]
            situacao = "exame";
        } else {                                   // [média < 4]
            situacao = "reprovado";
        }
        System.out.println(e.getNome() + ": " + situacao);  // Exibir situação
    }
}                                                  // nó final

05 Exemplo 2: um processo com raias, passo a passo

Agora um processo de verdade, com várias pessoas envolvidas: o caminho de um pedido na Cantina Online, do carrinho até a retirada no balcão.

Descrição do processo

O cliente monta o carrinho e confirma o pedido. O sistema calcula o total e solicita o pagamento; o cliente paga com Pix. Se o pagamento for recusado, o pedido é cancelado. Se for aprovado, três coisas acontecem ao mesmo tempo: o sistema registra a venda; o sistema gera o comprovante e o envia por e-mail; a cozinha prepara os lanches e embala o pedido. Quando a venda está registrada e o pedido embalado, o sistema avisa que o pedido está pronto; o cliente recebe o aviso e retira no balcão.

  1. Liste as ações e quem faz cada uma

    Transforme cada frase em uma ação com verbo no infinitivo e anote o responsável. Essa tabela já é meio diagrama.

    AçãoResponsávelObservação
    Montar carrinho, Confirmar pedido, Pagar com Pix, Retirar no balcãoCliente—
    Calcular total, Solicitar pagamento, Cancelar pedidoSistemaCancelar só se recusado.
    Registrar venda, Gerar comprovante, Enviar por e-mailSistemaEm paralelo com a cozinha.
    Preparar lanches, Embalar pedidoCozinhaEm paralelo com o sistema.

  2. Desenhe o início e o caminho principal

    Comece pelo nó inicial e ligue as ações do “caminho feliz” com fluxos de controle, na ordem em que acontecem. Não se preocupe ainda com decisões.

  3. Acrescente as decisões e suas guardas

    Depois de “Pagar com Pix” existe uma escolha: o pagamento foi aprovado ou recusado? Desenhe um losango de decisão e escreva uma guarda em cada saída. O caminho [recusado] leva a “Cancelar pedido” e a um nó final.

  4. Represente o paralelismo, os objetos e os finais

    “Três coisas acontecem ao mesmo tempo” é sinal de fork. O e-mail não precisa terminar para o pedido seguir: esse caminho acaba num final de fluxo (⊗). Já a venda registrada e o pedido embalado precisam estar prontos antes do aviso: eles se encontram num join. O comprovante que passa de uma ação para outra aparece como nó de objeto, e o aviso ao cliente é um sinal enviado e depois aceito.

  5. Distribua as ações em partições (raias)

    Por fim, desenhe uma raia para cada responsável e confira se cada ação está na raia de quem a executa. As setas que cruzam raias mostram as passagens de bastão — pontos comuns de atraso e de erro no processo real.

  6. Revise com uma checklist

    • Há exatamente um nó inicial e todo caminho chega a um final (de atividade ou de fluxo)?
    • Toda saída de decisão tem guarda, e as guardas cobrem todos os casos sem se sobrepor?
    • Cada fork tem o join correspondente — ou os caminhos que não se juntam terminam em final de fluxo?
    • Os nomes das ações são verbos no infinitivo (“Calcular total”, e não “Total”)?
    • Cada ação está na raia de quem realmente a executa?

06 Na prática com a Astah

  1. Crie o diagrama

    Diagram › Activity Diagram.

  2. Monte o fluxo

    Na paleta, use Initial Node, Action, Control Flow, Decision/Merge Node, Fork/Join Node, Final Node e Flow Final Node. Para escrever a guarda, selecione o fluxo que sai da decisão e preencha o campo Guard nas propriedades — a Astah desenha os colchetes.

  3. Adicione as raias

    Use Partition (vertical ou horizontal) e arraste as ações para dentro da raia correta. Para renomear a raia, dê um duplo clique no cabeçalho.

  4. Objetos e sinais

    Object Node, Send Signal Action e Accept Event Action ficam na mesma paleta. Use com moderação: eles ajudam quando o dado ou o evento é importante para entender o processo.

07 Erros comuns

ErroComo corrigir
Saída de decisão sem guarda, ou guardas que se sobrepõem ([média ≥ 6] e [média ≥ 4]).Toda saída tem guarda; elas devem ser exclusivas. Use [else] para o restante.
Usar merge para reunir caminhos paralelos.Caminhos que saíram de um fork se reúnem num join.
Usar final de atividade no fim de um caminho paralelo.Ele encerraria tudo. Use final de fluxo (⊗) se só aquele caminho termina.
Ações com nome de substantivo (“Pagamento”).Ação é verbo: “Processar pagamento”.
Várias setas saindo de uma ação sem losango nem barra.Deixe explícito: é decisão (losango) ou paralelismo (barra)?
Diagrama com dezenas de ações de detalhe.Agrupe passos em uma ação mais geral e detalhe em outro diagrama.

08 Exercício com solução: matrícula em disciplina

Enunciado

O aluno solicita matrícula em uma disciplina. O sistema verifica se ele cumpre os pré-requisitos; se não cumprir, informa a recusa. Se cumprir, verifica se há vagas: havendo vaga, confirma a matrícula. Sem vaga, a coordenação avalia a abertura de uma vaga extra — se aprovar, a matrícula é confirmada; se negar, o sistema informa a recusa. Use raias para Aluno, Sistema e Coordenação.

Roteiro sugerido

  1. Liste as ações (verbos no infinitivo) e o responsável por cada uma.
  2. Marque as perguntas do texto (“cumpre?”, “há vaga?”, “aprovou?”): cada uma vira uma decisão.
  3. Repare que dois caminhos levam a “confirmar” e dois levam a “informar recusa”: o que usar para reuni-los?
Ver solução comentada
  • Três decisões, cada uma com guardas complementares ([atende]/[não atende], [há vaga]/[sem vaga], [aprova]/[nega]).
  • Dois merges evitam desenhar a mesma ação duas vezes.
  • Não há paralelismo: não existe “ao mesmo tempo” no enunciado, então não há fork nem join.

09 Autoteste

1. Qual a diferença entre o nó final de atividade e o final de fluxo?

O final de atividade (olho de boi) encerra a atividade inteira. O final de fluxo (círculo com X) encerra só o caminho que chegou até ele.

2. Um losango com duas entradas e uma saída é o quê?

Um nó de junção (merge): reúne caminhos alternativos.

3. Quando usar join em vez de merge?

Para reunir caminhos paralelos, que saíram de um fork. O join espera todos; o merge deixa passar cada um que chegar.

4. Para que servem as partições (raias)?

Para mostrar quem é responsável por cada ação: pessoa, setor ou sistema.

5. Qual o equivalente, em código, de uma decisão seguida de um merge?

Um if/else: a decisão escolhe o bloco e o merge é o ponto em que o código continua depois dele.
