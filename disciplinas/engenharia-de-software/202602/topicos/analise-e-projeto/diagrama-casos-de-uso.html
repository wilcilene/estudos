Antes de pensar em classes ou telas, é preciso responder a uma pergunta simples: quem vai usar este sistema, e para conseguir o quê? O diagrama de casos de uso responde em uma página; a documentação de cada caso de uso conta, passo a passo, como isso acontece — inclusive quando algo dá errado.

01 Para que serve o diagrama de casos de uso

O diagrama de casos de uso mostra o sistema de fora para dentro: quem usa o sistema (os atores) e o que cada um consegue fazer com ele (os casos de uso). Ele não mostra telas, classes nem banco de dados — só os objetivos que o sistema atende.

É normalmente o primeiro diagrama da análise, porque conversa diretamente com os requisitos funcionais: cada requisito do tipo “o cliente deve poder…” costuma virar um caso de uso ou um passo de um caso de uso.

As duas partes do trabalho com casos de uso
ParteO que éPara que serve
DiagramaO desenho com atores, elipses e relacionamentos.Visão geral: o “índice” do que o sistema faz e para quem.
Documentação (especificação)O texto de cada caso de uso: atores, pré e pós-condições, fluxo principal, fluxos alternativos, regras.O detalhe: é daqui que saem as telas, as classes, os testes e as estimativas.
O diagrama sozinho diz pouco

A especificação da UML define a notação do diagrama, mas o valor real está no texto de cada caso de uso. Uma elipse escrita “Finalizar pedido” não diz o que acontece se o pagamento for recusado — a documentação diz. Por isso esta página ensina as duas coisas.

02 As peças do diagrama

O diagrama de casos de uso tem poucas peças. Conheça cada uma antes de montar o exemplo.

  • Ator

    Boneco com um nome: um papel que alguém ou algo externo desempenha ao usar o sistema. Uma mesma pessoa pode ter vários papéis.

  • Ator como retângulo

    Retângulo com a palavra-chave «actor». Comum para sistemas externos (banco, serviço de e-mail), mas o significado é o mesmo do boneco.

  • Caso de uso

    Elipse com verbo no infinitivo + complemento. Representa um objetivo completo do ator, que entrega algo de valor para ele.

  • Fronteira do sistema

    Retângulo com o nome do sistema (o subject). Casos de uso ficam dentro; atores, fora.

  • Associação

    Linha contínua entre ator e caso de uso: o ator participa daquele caso de uso. Normalmente sem seta.

  • Inclusão («include»)

    Seta tracejada do caso base para o incluído. O comportamento incluído acontece sempre que o base executa.

    Em código: uma chamada de método obrigatória.

  • Extensão («extend»)

    Seta tracejada da extensão para o caso base. Acrescenta um comportamento opcional, sob uma condição, num ponto de extensão.

    Em código: um if que chama um trecho opcional.

  • Ponto de extensão

    Compartimento extension points dentro da elipse: lugares nomeados do fluxo em que extensões podem entrar.

  • Generalização

    Linha contínua com triângulo vazado, do mais específico para o mais geral. O filho herda todas as associações do pai. Vale para atores e para casos de uso.

    Em código: como extends.

Como dar nome

Ator: substantivo que indica o papel (Cliente, Gerente), nunca o nome de uma pessoa. Caso de uso: verbo no infinitivo + objeto, do ponto de vista do ator (Finalizar pedido, e não Processamento do pedido nem Tela de pagamento).

03 Include, extend e generalização

Estes três relacionamentos são a principal fonte de dúvidas. A figura mostra a direção de cada seta:

«include»«extend»
Quando aconteceSempre que o caso base executa.Só quando a condição da extensão é verdadeira.
Sentido da setaDo base para o incluído.Da extensão para o base.
O caso base funciona sozinho?Não: depende do incluído para ficar completo.Sim: a extensão é um acréscimo opcional.
Uso típicoComportamento repetido em vários casos de uso (ex.: pagar, verificar situação).Variações e opcionais (ex.: aplicar cupom, calcular multa).
Na documentaçãoUm passo diz “o sistema executa UC04”.O caso base marca o ponto de extensão; a extensão diz onde entra e a condição.
Teste rápido

Leia a frase “Para [caso base], é preciso [outro caso]”. Se faz sentido sempre, é «include». Se o certo é “Durante [caso base], às vezes, [outro caso]”, é «extend».

Não transforme o diagrama em fluxograma

Include e extend não servem para mostrar a ordem dos passos. Use-os com moderação: a ordem e os detalhes pertencem à documentação (ou a um diagrama de atividades).

04 Passo a passo: o diagrama da Cantina Online

Enunciado — Cantina Online

O cliente consulta o cardápio do dia, monta o pedido no carrinho e o finaliza, pagando por Pix ou cartão por meio do sistema de pagamento do banco. Se tiver um cupom, pode aplicá-lo ao finalizar. Depois, acompanha o andamento e pode cancelar o pedido. O atendente da cozinha atualiza o status dos pedidos, e o gerente da cantina mantém o cardápio (inclui, altera e retira produtos).

  1. Encontre os atores

    Pergunte: quem usa o sistema? quem fornece ou recebe informações dele? que outros sistemas se comunicam com ele? No enunciado (marcações em amarelo) aparecem três papéis humanos e um sistema externo. Desenhe os atores fora do sistema: o ator principal à esquerda, os demais à direita.

  2. Liste os objetivos de cada ator

    Para cada ator, pergunte: o que ele quer conseguir com o sistema? Cada objetivo completo vira uma elipse com verbo no infinitivo. Desenhe a fronteira com o nome do sistema e coloque os casos de uso dentro dela. Registre também a lista em formato breve (tabela abaixo do passo 4).

  3. Ligue atores e casos de uso

    Associe cada ator aos casos de uso de que participa. O cliente participa de cinco; o atendente e o gerente, de um cada. O sistema de pagamento ainda não tem ligação: ele participa de um objetivo que vamos separar no próximo passo.

  4. Separe o que se repete e o que é opcional

    O pagamento é um comportamento completo, com seu próprio ator secundário, e poderia ser reaproveitado (por exemplo, numa futura recarga de créditos): vira Pagar pedido, incluído em Finalizar pedido. O cupom só entra quando o cliente tem um: vira a extensão Aplicar cupom de desconto, ligada ao ponto de extensão cupom, com a condição numa nota.

  5. Revise

    • Todo caso de uso está ligado a pelo menos um ator (diretamente, ou por meio de include/extend)?
    • Todo nome é verbo + objeto e representa um objetivo que entrega valor ao ator (e não um passo solto, como “Clicar em pagar”)?
    • Há algum requisito do enunciado sem caso de uso? E algum caso de uso sem requisito?
    • Include e extend estão no sentido certo?

05 A documentação do caso de uso

Cada elipse do diagrama ganha um texto: a especificação (ou descrição) do caso de uso. A UML não impõe um modelo de texto — cada empresa adota o seu —, mas os campos abaixo, popularizados por Alistair Cockburn, aparecem em praticamente todos os modelos.

Campos de uma especificação completa de caso de uso
CampoO que escreverDica
ID e nomeIdentificador (UC03) e o mesmo nome da elipse.O ID permite citar o caso de uso em outros documentos e testes.
Ator principalQuem tem o objetivo e dispara o caso de uso.Só um ator principal por caso de uso.
Atores secundáriosQuem participa ajudando (sistemas externos, outros papéis).Ex.: Sistema de pagamento.
Interessados e interessesQuem se importa com o resultado e o que cada um quer.Ajuda a descobrir regras e validações esquecidas.
Objetivo (resumo)Uma ou duas frases com o que o ator quer conseguir.Se não cabe em duas frases, talvez sejam dois casos de uso.
GatilhoO evento que inicia o caso de uso.Ex.: “o cliente toca em Finalizar pedido”.
Pré-condiçõesO que precisa ser verdade antes de começar. O caso de uso não verifica isso: assume.Não repita aqui o que é testado no fluxo.
Pós-condições (garantia de sucesso)O que é verdade quando termina com sucesso.Viram critérios de aceitação e casos de teste.
Garantia mínimaO que o sistema garante mesmo se falhar.Ex.: “nada é cobrado sem pedido registrado”.

Requisitos especiaisRequisitos não funcionais ligados a este caso de uso.Desempenho, segurança, acessibilidade.
Pontos de extensão e relacionamentosOnde extensões entram; quais casos inclui ou estende.Mantém texto e diagrama coerentes.

Três níveis de detalhe

Nem todo caso de uso precisa do modelo completo desde o início. Comece simples e detalhe os mais importantes ou arriscados:

FormatoTamanhoQuando usar
BreveUm parágrafo curto (como a lista do passo a passo acima).No início, para levantar e priorizar.
CasualAlguns parágrafos cobrindo o cenário principal e os alternativos.Casos de uso simples ou equipes pequenas.

06 Passo a passo: documentando “Finalizar pedido”

Vamos escrever a especificação completa do caso de uso mais importante da Cantina Online, campo a campo.

  1. Comece pelo cabeçalho

    Copie o ID e o nome do diagrama. Defina o ator principal (Cliente) e os secundários (Sistema de pagamento). Escreva o objetivo em uma frase, do ponto de vista do ator: “O cliente revisa o carrinho, paga e recebe a confirmação do pedido.”

  2. Defina as fronteiras: gatilho, pré e pós-condições

    Pergunte: o que precisa existir antes? (cliente identificado, carrinho com itens) e o que será verdade no fim, se der certo? (pedido PAGO, cozinha notificada). Some a garantia mínima: o que nunca pode acontecer, mesmo em caso de falha (cobrar sem registrar o pedido).

  3. Escreva o fluxo principal

    Descreva o cenário em que tudo dá certo em 5 a 10 passos. Cada passo é uma frase simples com sujeito — o ator ou o sistema — e verbo no presente. Descreva a intenção, não a interface: “o cliente confirma os itens”, e não “o cliente clica no botão verde”.

    Evite

    “O usuário clica em OK e aparece um pop-up com a lista de produtos em uma tabela azul.”

    Prefira

    “O sistema exibe os itens, as quantidades, os subtotais e o total.”

  4. Para cada passo, pergunte “e se…?”

    “E se um produto esgotou?” (4a), “e se o pagamento for recusado?” (6a), “e se ninguém pagar?” (E1). Cada resposta vira um fluxo alternativo (o objetivo ainda pode ser alcançado) ou de exceção (o caso de uso termina sem sucesso), numerado pelo passo onde nasce e dizendo para onde volta.

  5. Tire as regras do texto

    Valores e políticas que podem mudar (“10 minutos”, “três tentativas”, “R$ 5,00”) vão para a lista de regras de negócio, e o fluxo só cita o código (RN03). Assim, quando a cantina mudar o prazo, só uma linha muda.

  6. Ligue a documentação ao diagrama

    O «include» aparece como um passo (“o sistema executa UC04 Pagar pedido”). O «extend» aparece como um ponto de extensão marcado no passo 5 — o caso base não menciona o cupom; é a extensão que diz onde entra e sob qual condição.

07 Exemplo completo documentado

Este é o resultado. Leia o fluxo principal de ponta a ponta e depois cada alternativo, conferindo com a figura do passo 4 acima. Os códigos em amarelo remetem às regras de negócio no fim da ficha.

UC03

Finalizar pedido

Dados gerais de Finalizar pedido
Ator principalCliente
Atores secundáriosSistema de pagamento (por meio do UC04 Pagar pedido)
Interessados e interessesCliente: pagar rápido e ter certeza de que o pedido foi recebido. Cantina: receber apenas pedidos pagos e com produtos disponíveis.
ObjetivoO cliente revisa o carrinho, paga e recebe a confirmação do pedido.
GatilhoO cliente toca em “Finalizar pedido” no carrinho.
Pré-condiçõesO cliente está identificado no app. O carrinho tem pelo menos um item.
Pós-condições de sucessoO pedido está registrado com status PAGO, a cozinha foi notificada e o cliente recebeu o número do pedido.
Garantia mínimaNenhum valor é cobrado sem que o pedido fique registrado. Se o pedido não for concluído, o carrinho é preservado.
RelacionamentosInclui UC04 Pagar pedido. É estendido por UC06 Aplicar cupom de desconto no ponto de extensão cupom.

Fluxo principal (cenário de sucesso)

  1. O cliente solicita a finalização do pedido.
  2. O sistema exibe os itens, as quantidades, os subtotais e o total.
  3. O cliente confirma os itens.
  4. O sistema verifica se todos os produtos estão disponíveis RN02 e registra o pedido com status AGUARDANDO_PAGAMENTO.
  5. O sistema exibe o valor final a pagar. Ponto de extensão: cupom.
  6. O sistema executa o caso de uso UC04 Pagar pedido.
  7. O sistema registra o pagamento, muda o status para PAGO e notifica a cozinha.
  8. O sistema exibe o número do pedido e o tempo estimado de preparo RN05.
  9. O caso de uso termina.

Fluxos alternativos

3a O cliente quer alterar o carrinho
  1. O cliente escolhe “Alterar itens”.
  2. O sistema executa UC02 Montar pedido.
  3. O fluxo volta ao passo 2.
4a Um ou mais produtos esgotaram
  1. O sistema informa quais itens estão indisponíveis e os remove do carrinho.
  2. Se o carrinho ficou vazio, o caso de uso termina sem registrar o pedido; caso contrário, o fluxo volta ao passo 2.
4b O total é menor que o pedido mínimo
  1. O sistema informa o valor mínimo RN01.
  2. O fluxo volta ao passo 2.
6a O pagamento foi recusado
  1. O sistema informa o motivo da recusa e oferece nova tentativa.
  2. O cliente tenta de novo: o fluxo volta ao passo 6 (no máximo três tentativas RN04).

Fluxos de exceção

E1 Tempo de pagamento esgotado (no passo 6)
  1. O sistema cancela o pedido (status CANCELADO) após 10 minutos sem confirmação RN03.
  2. O sistema avisa o cliente e mantém os itens no carrinho.
  3. O caso de uso termina sem sucesso.
E2 Falha de conexão (em qualquer passo)
  1. O sistema informa que o pedido não foi enviado e preserva o carrinho.
  2. O caso de uso termina sem sucesso.

Regras de negócio

  • RN01 — O pedido mínimo é de R$ 5,00.
  • RN02 — Só podem ser vendidos produtos do cardápio do dia marcados como disponíveis.
  • RN03 — Pedido não pago em 10 minutos é cancelado automaticamente.
  • RN04 — São permitidas no máximo três tentativas de pagamento por pedido.
  • RN05 — O tempo estimado é a soma dos tempos de preparo dos itens, limitada a 40 minutos.

Requisitos especiais

  • A confirmação deve aparecer em até 3 segundos após a aprovação do pagamento.
  • A tela deve funcionar em celulares com tela a partir de 360 px de largura.

Frequência de uso

Alta: picos de cerca de 300 pedidos por hora nos intervalos entre aulas.

Questões em aberto

  • O cliente poderá agendar a retirada para outro horário?

09 Na prática com a Astah

  1. Crie o diagrama

    Diagram › UseCase Diagram.

  2. Fronteira, atores e casos de uso

    Na paleta, use System Boundary, Actor e UseCase. Para representar um sistema externo como retângulo, selecione o ator e altere sua forma de exibição (ícone ou retângulo com estereótipo) nas opções de apresentação.

  3. Relacionamentos

    Use Association entre ator e caso de uso; Include e Extend entre casos de uso (desenhe a partir do caso de origem: base para include, extensão para extend); Generalization entre atores.

  4. Pontos de extensão

    Clique com o botão direito no caso de uso base e adicione um Extension Point; a elipse ganha o compartimento correspondente.

  5. Documentação

    Cada elemento tem um campo de descrição no painel de propriedades; algumas edições da Astah oferecem ainda uma aba específica para a descrição do caso de uso, em formato de tabela. Se preferir, mantenha as fichas num documento separado e use o mesmo ID (UC03) nos dois lugares.

10 Erros comuns

ErroComo corrigir
Casos de uso que são passos ou telas: “Clicar em pagar”, “Tela de login”.Cada caso de uso é um objetivo completo do ator. Passos vão para o fluxo da documentação.
“Fazer login” ligado a todos os casos de uso por «include».Autenticação costuma ser uma pré-condição (“o cliente está identificado”), não um include em todo lugar.
Include e extend com a seta invertida.Include: base → incluído. Extend: extensão → base.
Usar include/extend para mostrar sequência (“depois de A vem B”).Ordem é assunto da documentação ou do diagrama de atividades.
O sistema aparece como ator de si mesmo.Atores são sempre externos. O próprio sistema é a fronteira.
Fluxo principal com detalhes de interface (“botão verde”, “menu à esquerda”).Descreva a intenção. Telas mudam; o objetivo não.
Fluxos alternativos que não dizem onde começam nem para onde voltam.Numere pelo passo de origem (4a) e termine com “volta ao passo X” ou “o caso de uso termina”.
Regras e números misturados no texto do fluxo.Extraia para a lista de regras de negócio (RN) e cite o código.

11 Exercício com solução: biblioteca

Enunciado

Na biblioteca da faculdade, os leitores — alunos e professores — consultam o acervo, reservam livros e renovam seus empréstimos. O bibliotecário realiza os empréstimos e registra as devoluções. Antes de emprestar ou renovar, é preciso verificar se o leitor não tem pendências. Na devolução, se houver atraso, o sistema calcula a multa. Alunos podem ter até 3 livros por 7 dias; professores, até 5 livros por 14 dias.

Tarefas: (1) desenhe o diagrama de casos de uso; (2) escreva a especificação completa de Realizar empréstimo.

Roteiro sugerido

  1. Alunos e professores fazem as mesmas coisas, com limites diferentes: como representar isso entre atores?
  2. “Antes de emprestar ou renovar, é preciso verificar…”: esse comportamento é obrigatório e aparece em dois lugares.
  3. “Se houver atraso, calcula a multa”: é obrigatório ou condicional?
  4. Onde ficam os limites de 3 e 5 livros: no fluxo ou nas regras de negócio?
Ver solução comentada
  • Generalização de atores: Aluno e Professor herdam as associações de Leitor; as diferenças ficam nas regras de negócio.
  • Include: Verificar situação do leitor é obrigatório e reaproveitado por dois casos de uso.
  • Extend: Calcular multa só acontece com atraso, no ponto de extensão atraso de Registrar devolução.
UC02

Realizar empréstimo

Dados gerais de Realizar empréstimo
Ator principalBibliotecário
Interessados e interessesLeitor: levar o livro rapidamente. Biblioteca: emprestar só para leitores em dia e controlar a devolução.
ObjetivoRegistrar a saída de um ou mais exemplares para um leitor.
Pré-condiçõesO bibliotecário está autenticado.
Pós-condições de sucessoO empréstimo está registrado com a data de devolução e os exemplares aparecem como emprestados.
RelacionamentosInclui Verificar situação do leitor.

Fluxo principal (cenário de sucesso)

  1. O bibliotecário informa o número de matrícula do leitor.
  2. O sistema executa Verificar situação do leitor.
  3. O bibliotecário informa o código de cada exemplar.
  4. O sistema verifica se cada exemplar está disponível e se o limite do leitor não foi atingido RN01.
  5. O sistema calcula a data de devolução RN02 e registra o empréstimo.
  6. O sistema emite o comprovante com os títulos e a data de devolução.

Fluxos alternativos

2a O leitor tem pendências (multa ou atraso)
  1. O sistema informa a pendência.
  2. O caso de uso termina sem empréstimo.
4a O exemplar está reservado para outro leitor
  1. O sistema informa a reserva e descarta o exemplar.
  2. O fluxo volta ao passo 3.
4b O limite de empréstimos foi atingido
  1. O sistema informa o limite.
  2. O fluxo continua no passo 5 apenas com os exemplares já aceitos.

Regras de negócio

  • RN01 — Alunos podem ter até 3 livros; professores, até 5.
  • RN02 — O prazo é de 7 dias para alunos e 14 dias para professores.

12 Autoteste

1. Um ator precisa ser uma pessoa?

Não. Ator é um papel externo ao sistema: pode ser uma pessoa, outro sistema (como o sistema de pagamento) ou um dispositivo.

2. “Emitir boleto” acontece sempre que “Fazer matrícula” acontece. Include ou extend?

«include», com a seta saindo de Fazer matrícula para Emitir boleto.

3. Para que serve um ponto de extensão?

Marca o lugar do fluxo do caso base em que uma extensão pode entrar, sem que o caso base precise conhecer a extensão.

4. Qual a diferença entre pré-condição e fluxo alternativo?

A pré-condição é assumida como verdadeira e não é verificada pelo caso de uso. Um fluxo alternativo trata algo que é verificado durante o caso de uso e pode dar diferente do esperado.

5. Como numerar o desvio que nasce no passo 6 do fluxo principal?

6a (e 6b, 6c… se houver outros no mesmo passo). Ele deve dizer para onde volta ou como o caso de uso termina.

6. Por que separar as regras de negócio do fluxo?

Porque as regras mudam com frequência. Separadas e numeradas, podem ser alteradas e testadas sem reescrever o fluxo.
