Caso Nº 16 · Princípio da Resolução · Aspectos Computacionais

Algoritmo de Resolução Proposicional

Chegou a hora de automatizar o investigador: um algoritmo que recebe as cláusulas e procura, sozinho, a contradição que fecha o caso.

Ao final deste caso, vocês vão saber
  • descrever o algoritmo de resolução por saturação e implementá-lo em poucas linhas;
  • explicar por que ele sempre termina na lógica proposicional e quanto ele pode custar;
  • usar estratégias que reduzem a busca: preferência unitária, conjunto de suporte e subsunção;
  • interpretar uma saturação sem □ como prova de que a conclusão não decorre das premissas.

A ideia: saturar

No Caso 15, eu escolhi com cuidado quais cláusulas resolver. Um computador não tem essa intuição, então a estratégia mais simples é a força: resolver todos os pares possíveis, acrescentar as resolventes ao conjunto e repetir. O processo para em uma de duas situações:

  • aparece a cláusula vazia □: o conjunto é insatisfatível (a conclusão foi provada);
  • uma rodada inteira não produz nenhuma cláusula nova: o conjunto está saturado e é satisfatível (a conclusão não decorre das premissas).
função resolucao(S):
    repita:
        novas ← ∅
        para cada par de cláusulas (C1, C2) em S:
            para cada resolvente R de C1 e C2:
                se R = □: retorne INSAT
                novas ← novas ∪ {R}
        se novas ⊆ S: retorne SAT          (saturou)
        S ← S ∪ novas

Uma implementação em Python

Usando a representação do Caso 14 (literal = inteiro com sinal, cláusula = frozenset), o algoritmo cabe numa tela:

def resolventes(c1, c2):
    saida = []
    for lit in c1:
        if -lit in c2:
            r = (c1 - {lit}) | (c2 - {-lit})
            if not any(-x in r for x in r):     # descarta cláusulas tautológicas
                saida.append(frozenset(r))
    return saida

def resolucao(clausulas):
    S = {frozenset(c) for c in clausulas}
    if frozenset() in S:
        return "INSAT"
    while True:
        novas = set()
        lista = list(S)
        for i in range(len(lista)):
            for j in range(i + 1, len(lista)):
                for r in resolventes(lista[i], lista[j]):
                    if not r:                     # cláusula vazia
                        return "INSAT"
                    novas.add(r)
        if novas <= S:
            return "SAT"
        S |= novas

# p → q, q → r, p ⊨ r ?   (1 = p, 2 = q, 3 = r; a última cláusula é ¬r)
print(resolucao([{-1, 2}, {-2, 3}, {1}, {-3}]))   # INSAT: a consequência vale

Acompanhando as rodadas

Exemplo que chega a □

Conjunto: {p, q}, {¬p, q}, {p, ¬q}, {¬p, ¬q} (as quatro combinações proibidas).

Rodada 1:
  {p, q}  + {¬p, q}   →  {q}
  {p, q}  + {p, ¬q}   →  {p}
  {¬p, q} + {¬p, ¬q}  →  {¬p}
  {p, ¬q} + {¬p, ¬q}  →  {¬q}
  (os outros pares só geram tautologias, descartadas)
Rodada 2:
  {q} + {¬q}          →  □     INSAT
Exemplo que satura sem □

Pistas: p ∨ q, ¬p ∨ q, q → r. Quero saber se p decorre delas, então acrescento {¬p}.

Inicial:   {p, q}  {¬p, q}  {¬q, r}  {¬p}
Rodada 1:  {q}  {p, r}  {¬p, r}
Rodada 2:  {r}  {q, r}            (por exemplo, {q} + {¬q, r} → {r})
Rodada 3:  só aparecem cláusulas que já existem
Resultado: SAT, saturado sem □

A conclusão p não decorre das pistas. E vejam: p = F, q = V, r = V satisfaz tudo, inclusive ¬p. É o contraexemplo que a saturação garante existir.

Terminação e custo

Com n variáveis, cada variável pode aparecer numa cláusula positiva, negativa ou ausente (cláusulas tautológicas são descartadas). Então existem no máximo 3ⁿ cláusulas diferentes. Como o conjunto só cresce e é limitado, o algoritmo sempre termina: na lógica proposicional, a resolução é um procedimento de decisão.

O lado ruim é o tamanho desse limite. Cada rodada compara todos os pares, e o conjunto pode crescer exponencialmente. Isso não é defeito da implementação: Haken provou em 1985 que existem fórmulas insatisfatíveis (como o princípio da casa dos pombos: n + 1 pombos não cabem em n casas sem dividir) cujas refutações por resolução têm tamanho exponencial, qualquer que seja a ordem escolhida. Isso combina com o que vimos no Caso 12: SAT é NP-completo.

Estratégias que cortam a busca

EstratégiaIdeiaPor que ajuda
Preferência unitáriaResolver primeiro com cláusulas de um literal.A resolvente é sempre menor que a outra cláusula: o conjunto encolhe em direção a □. É a propagação unitária do DPLL.
Conjunto de suporteToda resolução usa pelo menos uma cláusula que vem de ¬C (ou de uma resolvente dela).Premissas consistentes entre si não produzem □ sozinhas; a busca fica focada na pergunta. Continua completa.
SubsunçãoDescartar D quando existe C ⊆ D.Remove cláusulas redundantes antes que elas gerem mais redundância.
Eliminar tautologiasDescartar cláusulas com p e ¬p.Elas são sempre verdadeiras e nunca ajudam a chegar a □.

Um detalhe que eu acho bonito: quando o DPLL do Caso 12 responde INSAT, a árvore de busca dele corresponde a uma refutação por resolução. E os resolvedores modernos (CDCL) aprendem cláusulas novas a cada conflito exatamente por resolução. As duas ideias que vocês estudaram separadas trabalham juntas na prática.

Erro comum

Achar que “não encontrei □” é o mesmo que “a conclusão é falsa”. Saturar sem □ mostra só que a conclusão não é consequência das premissas: existe um cenário em que as pistas valem e a conclusão falha. Ela pode até ser verdadeira no envelope real; vocês só ainda não têm pistas para garantir.

No Detetive

Um assistente de anotações automático faria assim: juntar as regras do envelope (Caso 12), as pistas da partida e a negação da acusação que vocês pretendem fazer, por exemplo {¬J} para “foi o Jardineiro”, e rodar resolucao com conjunto de suporte. Se sair INSAT, a acusação é segura. Se sair SAT, o próprio estado saturado aponta um envelope compatível com tudo em que o culpado é outro, e a acusação seria um chute.

Exercício 1 · Trace o algoritmo

Tracem as rodadas para {p}, {¬p, q}, {¬q}.

Ver resposta

Rodada 1: {p} + {¬p, q} → {q}; {¬p, q} + {¬q} → {¬p}. Rodada 2: {q} + {¬q} → □ (ou {p} + {¬p} → □). INSAT.

Exercício 2 · Conjunto de suporte

Premissas: {¬a, b}, {¬b, c}, {a}, {d, e}, {¬e, d}. Conclusão: c. Usando conjunto de suporte, que resoluções vocês fazem? As cláusulas com d e e chegam a ser usadas?

Ver resposta

Suporte inicial: {¬c}. {¬c} + {¬b, c} → {¬b}; {¬b} + {¬a, b} → {¬a}; {¬a} + {a} → □. Três passos, e as cláusulas sobre d e e nunca entram: sem a estratégia, o algoritmo também resolveria {d, e} com {¬e, d} à toa.

Exercício 3 · Limite de cláusulas

Com 3 variáveis, quantas cláusulas não tautológicas distintas existem, contando a vazia? E com 20 variáveis, aproximadamente?

Ver resposta

3³ = 27. Com 20 variáveis, 3²⁰ ≈ 3,5 bilhões. O algoritmo termina, mas o limite deixa claro por que estratégias são indispensáveis.

Para guardar
  • Saturação: resolver todos os pares até achar □ (INSAT) ou não gerar nada novo (SAT).
  • Na lógica proposicional, sempre termina: no máximo 3ⁿ cláusulas.
  • O pior caso é exponencial (casa dos pombos), coerente com a NP-completude de SAT.
  • Preferência unitária, conjunto de suporte e subsunção tornam a busca viável.
  • Saturar sem □ = a conclusão não é consequência; existe contraexemplo.
